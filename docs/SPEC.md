# DEEP LINE 개발 명세서 (코딩 에이전트용)

2026-10-27

이 문서는 코딩 에이전트가 DEEP LINE을 마일스톤 순서대로 구현하기 위한 명세다. 게임의 배경과 의도는 `docs/DESIGN.md`(DEEP LINE 게임 설계서)를 따르고, 두 문서가 충돌하면 이 문서가 우선한다.

## 0. 작업 규칙

에이전트는 마일스톤을 순서대로 하나씩 끝내고, 마일스톤마다 멈춰서 사람의 검토를 받는다. 아래 규칙은 모든 마일스톤에 적용된다.

1. **순서를 지킨다.** 현재 마일스톤의 완료 기준을 모두 통과하기 전에는 다음 마일스톤을 시작하지 않는다.
2. **우선순위는 시뮬레이션 정확성 > 조작감 > 비주얼이다.** M5 전까지는 회색 상자 그래픽만 쓴다.
3. **시뮬레이션은 결정론적이어야 한다.** 시드 없는 난수, 실제 시각, 프레임 시간을 시뮬레이션 코어에서 쓰지 않는다.
4. **수치는 데이터 파일에 둔다.** 소비 전력, 유입량, 임계값 같은 튜닝 값을 코드에 하드코딩하지 않는다.
5. **테스트가 통과해야 끝난 것이다.** 모든 커밋에서 `dotnet test`가 통과해야 한다.
6. **모르는 결정은 가정하고 기록한다.** 이 문서에 없는 결정은 합리적으로 가정해서 진행하고, `docs/DECISIONS.md`에 날짜, 결정, 이유를 남긴다. 되돌리기 어려운 결정만 멈추고 묻는다.
7. **마일스톤이 끝나면 보고서를 쓴다.** `docs/reports/M<번호>.md`에 구현한 것, 실행 방법, 플레이 방법, 테스트 결과, 알려진 문제, 사람이 확인해야 할 것(특히 조작감)을 적는다.
8. **조작감은 사람이 판단한다.** 에이전트는 시뮬레이션을 테스트로 검증하고, 손맛과 소리는 보고서에 '확인 요청'으로 넘긴다.

## 1. 제품 요약

DEEP LINE은 1930년대 디젤펑크 세계의 소형 해저 케이블 수리 잠수함 안에서, 계통 고장을 진단하고 고치며 살아남는 1인칭 수리 시뮬레이션이다. PC 데스크톱, 1인용, 싱글플레이.

구현할 때 판단 기준이 되는 원칙은 다음과 같다.

- **수리가 핵심 재미다.** 다른 시스템은 수리를 더 흥미롭게 만들기 위해 존재한다.
- **플레이어는 잠수함 밖으로 나가지 않는다.** 바깥과는 현창, 소나, 조작팔, 윈치 같은 도구로만 닿는다.
- **잠수함은 작다(실내 약 8m).** 디테일은 잠수함 내부에만 쏟고, 보급, 임무, 바깥 세계는 단순하게 만든다.
- **고장에는 원인이 있다.** 고장은 부품 상태 변화로만 주입하고, 증상은 시뮬레이션 규칙에서 저절로 나와야 한다. 각본으로 증상을 띄우지 않는다.
- **큼직하지만 캐주얼하지 않게.** 수리 한 번은 진단, 두세 단계의 손작업, 시험으로 끝나지만 순서를 틀리면 대가가 있다.
- **손상은 임무 사이에 초기화된다.** 수면으로 돌아오면 회사가 전부 고친다. 대신 임무 중의 응급 수리는 항해 도중 다시 고장 날 수 있다. 조난 파트(6장)에는 초기화가 없다.

## 2. 기술 스택과 저장소 구조

엔진은 Godot 4.7 .NET 빌드, 언어는 C#이다. 시뮬레이션 코어는 Godot에 의존하지 않는 순수 .NET 라이브러리로 분리한다.

| 항목 | 선택 |
| --- | --- |
| 엔진 | Godot 4.7 (.NET 빌드), Forward+ 렌더러 |
| 언어 | C#. .NET SDK 버전은 Godot 4.7 .NET 빌드가 요구하는 버전을 따른다 |
| 대상 플랫폼 | Windows 데스크톱 우선, 이후 Linux와 macOS. 웹은 대상이 아니다 |
| 테스트 | xUnit (`dotnet test`) |
| 데이터 | JSON 파일. 스키마는 8절 |
| 버전 관리 | Git. 마일스톤마다 태그(`m0`, `m1` …) |

```

│  ├─ scenes/            # submarine.tscn, panels, interactables
```

## 3. 아키텍처

시뮬레이션 코어가 모든 판정을 하고, Godot 층은 입력을 명령으로 바꿔 넘기고 상태를 받아 보여주기만 한다. 둘 사이는 `SimRunner` 하나로만 연결된다.

```
┌───────────────────────┐   명령    ┌──────────────────┐   명령    ┌────────────────────────────┐
│ Godot 층              │ ────────▶ │ SimRunner        │ ────────▶ │ 시뮬레이션 코어 (순수 .NET) │
│ - 상호작용            │           │ - 고정 틱 20Hz   │           │ - 계통 8개                  │
│   (잡기, 돌리기,      │ ◀──────── │ - 명령과 상태    │ ◀──────── │ - 부품과 수리 절차          │
│    작업 시점)         │   상태    │   전달           │   상태    │ - 소음과 기믹 (상태 기계)   │
│ - 표현 (계기, 상황판, │           └──────────────────┘           │ - 고장 주입                 │
│   조명, 소리)         │                                          └────────────────────────────┘
│ - UI (매뉴얼, 메모장) │                                              ▲ 읽기          ▲ 검증
└───────────────────────┘                                           data/        sim.tests
```

코어는 Godot을 참조하지 않으므로 `data/`만 읽어서 `sim.tests`로 단독 검증할 수 있다.

### 코어 인터페이스 (초안)

```csharp
public interface ISimulation
{
    void Load(GameData data, int seed);
    void Apply(Command command);           // 플레이어 행동. 다음 틱에 반영
    void Step();                           // 고정 틱 1회 (0.05초)
    SimSnapshot Snapshot { get; }          // 표현용 읽기 전용 상태
    IReadOnlyList<SimEvent> DrainEvents(); // 경보, 단선, 감전, 폭발 등
    long Tick { get; }
    ulong StateHash();                     // 리플레이 테스트용
}
```

- `Command`는 직렬화 가능해야 한다. 리플레이는 (시드, 틱별 명령 목록)으로 재현한다.
- 상황판이 보여주는 값은 `Snapshot`의 진짜 값이 아니라 센서 부품을 거친 값이다(센서 고장 반영).
- `SimRunner`는 프레임 시간을 누적해서 정해진 틱 수만큼 `Step()`을 호출한다. 시간 가속은 틱 수를 늘리는 방식이다.

## 4. 시뮬레이션 모델

계통마다 몇 개의 상태 변수와 단순한 규칙으로 돌아가는 모델이다. 정밀한 물리가 아니라 원인과 결과의 일관성이 목표다. 아래 수치는 전부 `data/`의 튜닝 값이고, 출발점일 뿐이다. 실제 물리보다 빠르게 진행되도록 게임 배율이 들어가 있다.

### 시간

- 고정 틱 20Hz(틱당 게임 시간 0.05초). 게임 시간 1초는 실제 1초다.
- 이동 구간의 시간 가속(×4, ×8)은 프레임당 틱 수를 늘려서 구현한다. 결정론은 그대로 유지된다.
- 임무 한 판의 목표 길이는 20~40분이다.

### 부품

- 고장 날 수 있는 모든 것은 `Part`다. 상태는 `Normal`, `Warning`, `Fault`, `Broken` 네 단계다.
- `wear`(0~1)는 가동 시간 × 부하 × 환경(온도, 습기) × 품질 계수로 쌓인다.
- 상태는 `wear` 임계값(0.5 주의, 0.8 고장, 1.0 파손)이나 주입된 고장으로 정해진다.
- 품질 계수는 정품 1.0, 응급 4.0이다. 클수록 빨리 닳는다.

### 장비 초기값

축전지 용량은 1,200Wh(가안)이다.

| 장비 | 회로 | 소비 전력 (W) | 소음 |
| --- | --- | --- | --- |
| 실내 조명 | C1 조명 | 40 | 0 |
| 송풍 팬 | C2 생명유지 | 60 | 5 |
| 산소 화로 점화기 | C2 생명유지 | 10 | 2 |
| 전동 배수 펌프 | C3 배수 | 300 | 15 |
| 계통 상황판 | C4 감각 | 30 | 0 |
| 청음기 | C4 감각 | 20 | 0 |
| 탄소 아크 탐조등 | C4 감각 | 400 | 8 |
| 소나 발신(1회 1초) | C4 감각 | 150 | 30 |
| 자이로컴퍼스 | C5 항법 | 50 | 3 |
| 기계식 항법 계산기 | C5 항법 | 20 | 4 |
| 갈고리 윈치 | C6 케이블 장비 | 600 | 30 |
| 사이펀 기록기 | C6 케이블 장비 | 15 | 1 |
| 납땜인두 | C7 공구 | 80 | 0 |
| 추진 전동기(최대) | C8 추진 | 800 | 20 |

### 전력

- 축전지는 6셀이다. 셀마다 `charge`(0~1)와 `health`(0~1)가 있다.
- 버스 전압(정규화) V = (살아 있는 셀 수 ÷ 6) × f(평균 charge). f는 charge 0.2 아래에서 급격히 떨어진다.
- 장비는 V가 장비의 최소 전압 이상일 때만 작동한다. 실내 조명 밝기는 V에 비례한다(전압이 떨어지면 등이 어두워진다).
- 죽은 셀은 점퍼로 건너뛰게 연결할 수 있다. 그러면 전압은 낮아지지만 셀 하나가 회로 전체를 막지 않는다.

### 배전반

- 회로는 C1~C8 여덟 개다. 회로마다 칼날 스위치와 퓨즈가 있다.
- 회로 전류 I = 회로 소비 전력 ÷ V. I가 퓨즈 정격을 2초 이상 넘으면 퓨즈가 끊긴다. 막힌 모터처럼 부하가 치솟는 고장이 퓨즈를 끊는다.
- 배선의 습기가 임계값을 넘으면 누전이 생긴다. 누설 전류가 전력을 낭비하고, 퓨즈를 끊고, 만지면 감전된다.
- 접점이 부식되면 접점 저항이 올라 발열하고, 연기와 냄새가 난다.

### 침수와 배수

- 구역은 전방, 중앙, 후방, 빌지 네 곳이다. 물은 먼저 빌지로 모이고, 빌지 용량(600L)을 넘으면 바닥 위로 차오른다. 바닥 위 수위는 구역 바닥 면적(구역당 약 8m²)으로 계산한다.
- 누수 지점마다 유입량 q = k × a × √d. a는 누수 면적(cm²), d는 수심(m), k = 0.02L/s(가안). 수심 400m, 1cm² 누수면 분당 약 24L다.
- 전동 펌프 배출량은 정격 2.0L/s × 부품 상태에 따른 효율. 수동 펌프는 한 번 펌질에 1.5L.
- 후방 해치를 닫으면 후방 구역의 물이 다른 구역으로 넘어가지 않는다.
- 빌지 수위가 400L를 넘으면 축전지 셀이 잠기기 시작하고 염소가 발생한다.

### 공기

실내 부피는 30m³(가안)다. 아래 비율은 게임 배율이 적용된 값이다.

| 변수 | 변화 | 효과 임계값 |
| --- | --- | --- |
| 이산화탄소 (%) | 사람 +0.1/분. 흡수통이 팬과 함께 −0.15/분. 흡수통 하나는 6%분을 흡수하면 포화 | 2: 숨소리 거칠어짐, 4: 시야 흐림, 6: 조작 느려짐, 8: 의식 상실 |
| 산소 (%) | 사람 −0.08/분. 산소 양초 하나가 10분 동안 +0.4/분 | 17: 숨참, 14: 시야 좁아짐, 11: 의식 상실 |
| 염소 (ppm) | 잠긴 축전지 셀 수에 비례해 발생. 팬이 서서히 희석 | 10: 기침과 눈물, 30: 심각, 60: 의식 상실 |
| 수소 (%) | 축전지 충전 중 +0.05/분. 팬이 제거 | 4 이상에서 불꽃(접점 아크, 퓨즈 단선, 납땜)이 튀면 폭발 |

### 선체

- 누수 지점은 리벳 이음 12곳, 현창 2곳, 프로펠러 축 패킹 1곳, 선체 밸브 4곳, 케이블 챔버 바깥 문 1곳이다.
- 지점마다 `integrity`(0~1)가 있다. 응력 s = (d ÷ 설계 수심) × (1 + 감기 하중) × 해류 계수. s가 1을 넘으면 integrity가 (s − 1)에 비례해 줄어든다.
- 누수 면적 a = 최대 누수 면적 × (1 − integrity)². 작은 손상은 거의 새지 않는다.
- **응급 패치**(버팀목, 쐐기)는 a를 10%로 줄이지만, 패치 내구도가 응력에 비례해 줄어들고 0이 되면 원래 누수로 돌아간다. 이것이 '응급 수리의 재발'이다.
- **정식 수리**(코킹, 밀봉 교체)는 integrity를 0.9로 되돌린다.

### 열

- 장비마다 온도가 있다. 발열 = 소비 전력 × 손실 계수 × (1 + wear), 냉각 = (장비 온도 − 주변 온도) × 냉각 계수.
- 과열 임계값을 넘으면 wear가 3배로 쌓이고 연기와 냄새가 난다.

### 소음

- 소음은 0~100 단위다. 현재 소음 N = 가동 중인 장비 소음의 합 + 행동이 낸 순간 소음.
- 행동 소음 초기값: 퓨즈 교체 2, 렌치 3, 줄질 10, 수동 펌프 펌질 25, 역세척 35, 망치 타격 40, 코킹 45.
- 누적 소음 A는 dA/dt = N − 0.1 × A로 변한다. A가 기믹(소리 사냥꾼 등)의 방아쇠다.

### 부력과 자세 (M2부터)

- 순 부력 = 기본 부력 − (밸러스트 물 + 침수량). 수직 속도는 순 부력에 비례하고 상한이 있다.
- 기울기는 앞뒤 물 무게의 차이에 비례한다. 10°를 넘으면 고정하지 않은 공구가 굴러가고, 25°를 넘으면 걷기가 어려워진다.

### 고장 주입과 초기화

- 고장은 `FaultInjector`가 부품 상태를 바꾸는 방식으로만 주입한다. 시나리오 파일은 (틱, 부품 ID, 고장 ID)의 목록이다.
- 무작위 고장은 장, 수심, 부품 wear에 따른 발생률로 뽑는다. 시드는 임무마다 고정한다.
- 임무가 끝나면 모든 계통을 초기 상태로 되돌린다. 조난 파트에는 초기화가 없다.

## 6. 수리 절차 모델

수리는 데이터로 정의된 절차(`RepairProcedure`)이고, 절차는 전제 조건과 대가가 붙은 단계(`RepairStep`)의 목록이다. 시뮬레이션 코어가 단계를 검증하고 결과를 적용한다. Godot 층은 단계를 손동작으로 보여줄 뿐 판정하지 않는다.

### 단계 종류

| 단계 | 하는 일 | 예 |
| --- | --- | --- |
| Inspect | 정보를 얻는다. 상태는 바꾸지 않는다 | 전압계로 찍기, 청진기 대기, 비중계 재기 |
| Isolate | 위험원을 끊는다 | 회로 스위치 내리기, 밸브 잠그기, 압력 빼기 |
| Open | 덮개나 패널을 연다 | 펌프 덮개 볼트 풀기 |
| Remove | 부품을 뺀다 | 끊어진 퓨즈, 닳은 베어링 |
| Work | 부품을 손본다 | 닦기, 줄질, 패킹 감기, 접점 다듬기 |
| Install | 부품을 넣는다. 품질(정품, 응급)이 기록된다 | 새 퓨즈, 쐐기 |
| Fasten | 조인다. 순서가 있을 수 있다 | 플랜지 볼트를 별 모양 순서로 |
| Close | 덮개를 닫는다 | |
| Test | 장비를 돌려 결과를 확인한다 | 펌프 가동, 배수량 확인 |

### 단계의 속성

- `tool`: 필요한 도구. 도구는 잃어버리거나 망가지지 않는다.
- `requires`: 전제 조건. 예: 회로가 꺼져 있을 것, 배관 압력이 0일 것.
- `hazard`: 전제 조건을 어기면 일어나는 일. 감전(화면 흔들림, 잠시 조작 불가, 체력 손상), 물 분출(순간 유입), 불꽃(수소가 있으면 폭발).
- `duration`: 게임 시간(초). 이동 중이 아니어도 시뮬레이션은 계속 흐른다.
- `noise`: 단계가 내는 소음.
- `consumes`: 쓰는 부품이나 자재. 일반 예비 부품과 자재는 선내 사물함에 충분하고, 진공관 같은 특수 부품만 재고가 한정된다. 부품을 만드는 제작 과정은 없다.

### 결과

- 절차가 끝나면 부품의 상태, wear, 품질이 바뀐다. 응급 수리는 품질 '응급'과 패치 내구도를 남긴다.
- 순서를 지키지 않은 조립(예: 볼트를 한쪽부터 조임)은 성공처럼 보이지만 미세 누수 같은 숨은 결함을 남긴다.

### 예시: ELC-01 정식 수리

```json
{
  "id": "proc.fuse.replace",
  "fault": "ELC-01",
  "grade": "proper",
  "steps": [
    {"type": "Inspect", "target": "fuse.{circuit}", "tool": "voltmeter", "duration": 3, "noise": 0},
    {"type": "Isolate", "target": "switch.{circuit}", "duration": 1, "noise": 2},
    {"type": "Remove", "target": "fuse.{circuit}", "requires": ["circuit.{circuit}.off"],
     "hazard": "shock", "duration": 2, "noise": 1},
    {"type": "Install", "target": "fuse.{circuit}", "consumes": ["fuse"], "duration": 2, "noise": 1},
    {"type": "Test", "target": "switch.{circuit}", "duration": 1, "noise": 2}
  ]
}
```

### 예시: HUL-01 응급 수리

```json
{
  "id": "proc.rivet.wedge",
  "fault": "HUL-01",
  "grade": "temporary",
  "steps": [
    {"type": "Inspect", "target": "leak.{point}", "duration": 2, "noise": 0},
    {"type": "Install", "target": "leak.{point}", "consumes": ["wood_wedge"], "tool": "mallet",
     "duration": 6, "noise": 18},
    {"type": "Install", "target": "shore.{point}", "consumes": ["timber_shore"], "duration": 8, "noise": 10}
```

## 7. 상호작용과 조작

화면에 떠 있는 UI는 최소로 하고, 정보는 잠수함 안의 물건(상황판, 계기, 매뉴얼, 계산기)으로 전달한다. 마우스 움직임이 그대로 손의 움직임이 되는 물리적 조작감이 목표다.

### 상호작용 물체 종류

| 종류 | 조작 | 예 |
| --- | --- | --- |
| Switch | 클릭 후 위아래로 끌기 | 칼날 스위치, 토글 |
| Valve | 클릭 후 원을 그리며 돌리기. 바퀴 수가 정해져 있다 | 밸러스트 밸브, 선체 밸브 |
| Lever | 클릭 후 한 축으로 끌기 | 윈치 브레이크, 수동 펌프 손잡이 |
| Cover | 볼트를 푼 뒤 젖히기 | 펌프 덮개, 분기함 |
| Socket | 꽂고 빼기 | 퓨즈, 진공관, 탄소봉 |
| Fastener | 도구를 들고 클릭 후 돌리기 | 볼트, 조임 너트 |
| ToolUse | 도구를 들고 대상에 대기 | 청진기, 전압계, 비중계, 코킹 정 |
| Readable | 가까이 보기 | 계기, 상황판, 매뉴얼, 메모 |

### 시점

- **이동 시점**: 1인칭. 걷기, 웅크리기(바닥 아래), 해치 통과.
- **작업 시점**: 수리 가능한 장비를 선택하면 카메라가 장비 앞의 지정 위치로 붙고, 분해 단계가 보인다. 다시 누르면 이동 시점으로 돌아간다.

### 계통 상황판 (전방 조종 구역)

- 8대 계통마다 표시등 하나(평상시 꺼짐, 주의 노랑, 고장 빨강)와 대표 계기가 있다. 이상이 생기면 경보 벨이 울린다.
- 상황판도 부품이다. SNS-01, SNS-02 고장이 나면 표시가 꺼지거나 틀린다. 상황판은 시뮬레이션의 '진짜 상태'가 아니라 '센서가 읽은 값'을 보여줘야 한다.
- 구역마다 붉은 경고등이 따로 있어서, 상황판이 고장 나도 어느 구역에 문제가 있는지는 알 수 있다.

### 매뉴얼 바인더

- 조종석 옆에 늘 꽂혀 있는 게임 속 책이다. 정상 절차, 비상 절차, 계통도, 케이블 위치 계산 공식, 부품 목록이 들어 있다.
- 페이지는 `data/manual/`의 마크다운으로 만든다. 일부 절차는 개정 전 내용이 남아 틀려 있다(데이터에 표시).

### 선내 계산 도구

케이블 위치 계산은 매뉴얼의 공식에 측정값을 넣는 수준이다. 계산을 돕는 도구를 선내에 둔다.

- **저항 측정 브리지**: 케이블의 저항을 재는 장치. 다이얼을 돌려 검류계 바늘을 0에 맞추면 저항값이 읽힌다.
- **기계식 탁상 계산기**: 숫자 다이얼을 맞추고 손잡이를 돌리는 1930년대식 계산기. 곱셈과 나눗셈을 한다.
- **계산자**: 빠르지만 정밀도가 낮다.
- **노모그램 도표**: 벽에 붙은 계산 도표. 자를 대면 값이 읽힌다. 예: 수심별 누수량, 축전지 잔량별 남은 시간.

### 메모장과 체크리스트

- **메모장**: 플레이어가 직접 적는 공책(자유 텍스트). 측정값, 계산, 고장 기록을 적는다.
- **체크리스트**: 출항 점검과 비상 절차. 항목을 하나씩 짚어가며 체크한다.

### 몸의 상태

이산화탄소, 산소, 염소, 감전, 추위를 화면 효과(흐림, 시야 축소, 흔들림)와 숨소리로 표현한다. 체력 바 같은 숫자 UI는 쓰지 않는다.

### 기본 조작 (가안)

| --- | --- |
| WASD, 마우스 | 이동, 시선 |

| 왼쪽 버튼 누른 채 끌기 | 잡고 조작하기 |

## 8. 데이터 스키마

게임의 모든 콘텐츠와 튜닝 값은 `data/`의 JSON으로 정의하고, 시뮬레이션 코어가 시작할 때 읽어서 검증한다. 아래는 최소 형태이고, 에이전트가 필요에 따라 필드를 늘리되 `docs/DECISIONS.md`에 기록한다.

| 파일 | 내용 |
| --- | --- |
| `devices.json` | 장비: 회로, 소비 전력, 최소 전압, 소음, 발열, 구성 부품 |
| `parts.json` | 부품: 종류, 마모 계수, 상태 임계값, 예비품 여부 |
| `faults.json` | 고장: ID, 대상 부품, 상태 변화, 증상 규칙 참조 |
| `procedures.json` | 수리 절차(6절 형식) |
| `hull.json` | 누수 지점: 위치, 구역, 최대 누수 면적, 설계 수심 |
| `tuning.json` | 공기, 침수, 소음 등 전역 계수와 임계값 |
| `missions.json` | 임무: 장, 수심, 케이블 구간, 할당량, 시드, 고장 발생률, 기믹 |
| `cards.json` | 보급 카드(종류와 장수는 미정. 시스템만 구현) |
| `manual/*.md` | 매뉴얼 페이지 |

```json
// devices.json (일부)
{
  "bilge_pump": {
    "circuit": "C3", "powerW": 300, "minVoltage": 0.6, "noise": 15,
    "heatFactor": 0.2, "parts": ["pump.motor", "pump.bearing", "pump.seal", "pump.intake", "pump.check_valve"],
    "zone": "aft"
  }
}
```

```json
// faults.json (일부)
{
  "WTR-01": {
    "part": "pump.intake", "set": {"state": "Fault", "clog": 1.0},
    "effects": ["pump.flowFactor = 1 - clog", "pump.loadFactor = 0.4"]
  }
}
```

`effects`는 문자열 식이 아니라 코드에 정의된 효과 규칙의 ID와 매개변수로 바꿔도 된다. 핵심은 고장이 '부품 상태 변화'로만 표현되고, 증상은 계통 규칙이 그 상태를 읽어 만든다는 점이다.

## 9. 임무, 케이블 작업, 보급

한 판은 '지시서 → 보급 선택 → 출항 점검 → 이동 → 케이블 작업 → 귀환 → 결산'이고, 그 사이 언제든 고장과 기믹이 끼어든다. 임무가 끝나면 모든 손상이 초기화된다.

### 임무 흐름

1. **지시서**: 사이펀 기록기 테이프로 들어온다. 케이블 구간, 할당량, 특이 사항.
2. **보급 선택**: 보급 카드 중 몇 장을 고른다. 장수와 종류는 미정이므로 데이터만 바꾸면 되게 만든다.
3. **출항 점검**: 체크리스트에 따라 회로를 올리고 계통을 깨운다.
4. **이동**: 해도 위의 케이블 노선을 따라 간다. 이동 구간은 시간 가속을 허용한다.
5. **케이블 작업**: 아래 절차.
6. **귀환과 결산**: 모선 도킹 지점으로 돌아오면 할당량을 평가하고 다음 임무로 넘어간다.

### 케이블 작업 절차

1. **측정**: 저항 측정 브리지로 케이블의 저항 R을 잰다.
2. **계산**: 매뉴얼의 공식에 넣는다. 고장 지점까지의 거리 d(km) = R(Ω) ÷ r(Ω/km). r은 케이블 종류별로 매뉴얼에 적혀 있다. 탁상 계산기나 계산자로 계산한다.
3. **이동**: 항법 계산기가 보여주는 노선상 거리로 그 지점까지 간다. 자이로나 계산기가 고장 나면 위치 오차가 생긴다.
4. **인양**: 갈고리 윈치를 내려 케이블을 건다. 현창과 탐조등으로 확인한다.
5. **접속**: 케이블 끝을 챔버로 끌어들이고, 바깥 문을 닫고, 챔버 물을 빼고, 안쪽 해치를 열어 심선을 잇는다. 접속은 수리 절차와 같은 방식(6절)으로 정의한다.
6. **시험 송신**: 사이펀 기록기로 시험 신호를 보내고, 깨끗한 물결선이 돌아오면 성공이다.

### 실패와 재시작

- 의식 상실, 폭발, 선체 붕괴, 시간 초과는 임무 실패다. 실패하면 그 임무를 처음부터 다시 한다.
- 조난 파트(6장)는 구간 단위로 같은 방식의 재시작 지점을 둔다.

### 보급

- 보급은 편의다. 어떤 수리나 임무도 보급 카드를 요구해서는 안 된다. 보급 없이도 게임 전체를 끝까지 진행할 수 있어야 한다.
- 카드 효과는 여섯 종류로 구현한다.
    - 좋은 도구: 해당 수리 단계의 시간, 소음, 전력 소모를 줄인다.
    - 진단 보조: 회로의 통전 여부나 누수 위치처럼 진단에 필요한 정보를 바로 보여준다.
    - 여유분: 산소 양초와 흡수제를 추가한다.
    - 사전 정비: 지정한 계통 부품의 wear를 0으로 시작해서 그 임무 동안 고장 확률을 낮춘다.
    - 정보: 정밀 해도(케이블 위치 오차 감소), 매뉴얼 부록(특정 고장의 진단 요령).
    - 고급 패치: 응급 수리의 패치 내구도가 줄지 않아 재발하지 않는다.
- 할당량 결과에 따라 다음 임무의 선택 장수가 바뀌는 규칙을 데이터로 둔다.

## 10. 기믹 구현 지침

기믹은 장마다 더해지는 규칙이고, 이전 기믹은 사라지지 않고 섞인다. 모든 기믹은 시뮬레이션 코어 안의 상태 기계로 구현하고, 반드시 예고 신호, 대응 방법, 그 대응의 대가를 가진다. 세부 수치와 연출은 해당 마일스톤에서 사람과 함께 조정한다.

| 기믹 | 장 | 방아쇠 | 예고 신호 | 대응과 대가 |
| --- | --- | --- | --- | --- |
| 회사 할당량 | 1 | 임무 시작 | 지시서 | 할당량 미달 시 다음 보급 감소. 위험한 추가 지시를 따를지 선택 |
| 부착물 | 2 | 임무 경과 시간 | 펌프 배수량과 냉각수 흐름의 점진적 감소 | 밸브 순서를 바꿔 역세척. 시끄러움 |
| 해류 | 2 | 해도의 해류 구역 진입 | 선체 삐걱임, 기울기계 흔들림 | 고정하지 않은 공구가 굴러간다. 이음새 응력 증가 |
| 소리 사냥꾼 | 3 | 누적 소음 A가 임계값 초과 | 청음기의 딸깍거리는 반향음이 점점 가까워짐 | 팬과 펌프까지 끄고 숨죽이기. 그동안 공기와 침수가 악화. 들키면 선체 충격으로 누수 발생 |
| 빛을 쫓는 것 | 4 | 현창 불빛, 탐조등, 섬광 | 현창 밖에서 흉내 내는 불빛 | 실내를 붉은 비상등으로 낮추고 손전등으로 수리 |
| 선체 감기 | 4 | 무작위 이벤트(장별 확률) | 수압계가 튐, 강철이 우는 소리 | 연쇄 리벳 누수. 선체 전기 충격으로 떼어내면 축전지를 크게 소모 |
| 거짓 신호 | 5 | 임무 중 무작위 | 보낸 적 없는 지시나 구조 요청 테이프 | 암호표로 검증. 가짜를 따르면 더 깊고 위험한 곳으로 |
| 거짓말하는 계기 | 5 | 계기 부품 드리프트 | 같은 값을 재는 계기끼리 불일치 | 대조와 영점 보정 |
| 선내 침입자 | 6 | 침수 구역 존재 | 빌지의 긁는 소리, 원인 모를 전기 고장 | 빌지 통로 막기, 갉힌 배선 수리 |
| 즉석 발전기 | 6 | 열수구 증기 발전기 가동 | 증기 압력계, 안전밸브 소리 | 과압과 과열 관리. 발전 중 소음과 수소 발생 |

### 소리 사냥꾼 상태 기계 (예시)

`Idle → Curious → Approaching → Searching → Leaving`

- A가 임계값 T1을 넘으면 Curious, T2를 넘으면 Approaching으로 간다.
- Approaching과 Searching 중에 현재 소음 N이 임계값을 넘으면 '들킴'이 되어 선체 충격(무작위 누수 지점 2~3곳의 integrity 감소)이 일어난다.
- 일정 시간 조용하면 Leaving으로 가고 다시 Idle이 된다.
- 상태마다 청음기 소리가 달라서, 플레이어는 귀로 상태를 읽는다.

## 11. 아트와 사운드 구현 지침

목표는 '어둑한 따뜻한 등이 켜진 차가운 강철 기계실'의 사실적인 분위기다. 유료 에셋은 쓰지 않는다. M5 전까지는 회색 상자 그래픽만 쓰고, 조명 규칙만 먼저 구현한다.

### 에셋 방침

- **절차적 생성 우선**: 실내는 대부분 배관, 패널, 리벳, 밸브 같은 산업용 하드서피스라 절차적으로 만들기 좋다. 배관은 경로를 따라 생성하고, 리벳과 용접선은 셰이더나 트림 시트로 처리한다.
- **모듈식 키트**: 배관 직관과 곡관, 플랜지, 밸브 핸들, 계기, 패널, 칼날 스위치, 퓨즈 소켓, 해치를 키트로 만들고 조합한다.
- **무료 자원**: CC0 재질과 HDRI(Poly Haven, ambientCG 같은 곳)는 써도 된다.
- **AI 3D 생성 도구(선택)**: 사이펀 기록기, 탁상 계산기 같은 상징 소품에만 쓸 수 있다. 쓰기 전에 상업적 이용 조건을 확인한다.
- 쓴 외부 자원은 출처와 라이선스를 `docs/ASSETS.md`에 전부 기록한다.

### 조명 규칙

- **평상시**: 밝지 않은 따뜻한 백열등.
- **고장**: 그 구역의 붉은 경고등과 상황판 표시등이 켜진다.
- **전압 강하**: 버스 전압 V에 비례해 실내등이 어두워지고 깜빡인다. 조명만 봐도 동력 상태를 느낄 수 있어야 한다.
- **바깥**: 청백색 아크 탐조등. 실내 불빛은 현창으로 새어 나간다.
- 조명 밝기와 경고등은 시뮬레이션 상태에서만 정해진다. 연출용으로 따로 켜지 않는다.

### 사운드

- **장비 소리는 상태에서 생성한다**: 펌프와 팬, 전동기는 회전수에 따라 음높이가 바뀌고, 마모되면 갈리는 성분이 섞인다. Godot의 `AudioStreamGenerator`로 합성하거나, 짧은 반복 샘플의 음높이와 필터를 조절한다.
- **선체**: 응력에 따라 삐걱임의 빈도와 음높이가 올라간다.
- **누수**: 위치가 있는 3D 소리. 방향만으로 어디서 새는지 찾을 수 있어야 한다.
- **바깥 소리**: 청음기를 켜야 들리는 소리와 선체를 통해 바로 들리는 소리를 구분한다.
- **음악**: 최소로 한다. 축음기 녹음판이 사실상 유일한 음악이다.
- 효과음 샘플도 CC0이거나 직접 합성한 것만 쓴다.

## 12. 마일스톤

여덟 개 마일스톤을 순서대로 진행하고, 끝날 때마다 사람이 검토한다. 전체 예상은 에이전트 작업 약 100~200시간, 사람 검토를 포함한 달력 기간 약 2~3.5개월이다. 이후의 밸런스 조정과 다듬기는 별도다.

| --- | --- | --- | --- | --- | --- |
| M0 시뮬레이션 코어 | 전력, 배전반, 침수, 공기, 소음 계통과 5절의 M0 범위 고장 | 시나리오 테스트 10개 통과, 같은 시드의 리플레이 일치 | 4~8시간 | 보고서 확인 | 1~2일 |

### 예상치를 읽는 법

- 에이전트 작업 시간은 에이전트가 실제로 코드를 쓰고 테스트를 돌리는 시간이다. 에이전트의 세션 길이와 사용 한도에 따라 달력 기간이 크게 달라진다.
- 시간을 가장 많이 잡아먹는 것은 코드가 아니라 사람의 판단이다. 조작감(M1), 그래픽과 소리의 취향(M5)은 에이전트가 스스로 검증할 수 없어서 왕복이 늘어난다.
- M0, M2, M4처럼 테스트로 검증되는 마일스톤은 예상보다 빨리 끝날 가능성이 높다.
- M1이 끝나는 시점이 '이 게임이 재밌는가'를 판단하는 첫 관문이다. 여기서 방향을 바꾸는 비용이 가장 싸다.

## 13. 테스트 전략

시뮬레이션은 Godot 없이 `dotnet test`만으로 전부 검증할 수 있어야 한다. 테스트는 네 층이다.

1. **단위 테스트**: 계통 규칙 하나하나. 예: 퓨즈 정격을 2초 넘기면 끊긴다, 펌프 효율 0이면 배수량 0, 흡수제가 포화되면 이산화탄소가 오른다.
2. **시나리오 테스트**: 고장을 주입하고 기대한 증상이 기대한 순서와 시간 안에 나타나는지 확인한다. 형식은 아래와 같다.
3. **리플레이 테스트**: 같은 시드와 같은 명령 기록이면 마지막 상태의 해시가 같아야 한다.
4. **해결 가능성 테스트**: 규칙 기반 자동 플레이어(머신러닝 아님)가 생성된 고장 조합에서 최소 한 가지 생존 경로를 찾는지 확인한다. M4부터 기믹 조합에도 적용한다.

```json
{
  "name": "축 패킹 누수가 배수 부담을 거쳐 축전지를 소모시킨다",
  "seed": 42,
  "depth": 300,
  "inject": [{"tick": 0, "fault": "HUL-03"}],
  "commands": [{"tick": 200, "cmd": "switch.C3.on"}],
  "expect": [
    {"byTick": 400, "assert": "zone.aft.water > 0"},
    {"byTick": 1200, "assert": "panel.lamp.water == 'warning'"},
    {"byTick": 6000, "assert": "battery.charge < start - 0.05"}
  ]
}
```

### Godot 쪽 확인

- 헤드리스로 주요 씬을 열고 일정 프레임을 돌린 뒤 오류 없이 종료되는지 확인하는 스모크 테스트를 둔다.
- 시뮬레이션 한 틱의 계산 시간은 1ms 미만을 목표로 한다.
- 조작감, 그래픽, 소리는 테스트 대신 마일스톤 보고서의 '사람 확인 요청' 항목으로 넘긴다.
