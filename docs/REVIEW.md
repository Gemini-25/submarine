# DEEP LINE 설계 검토

2026-10-27 · 대상: `docs/SPEC.md`, `docs/DESIGN.md`

## 결론

이 설계대로 가도 됩니다. 시뮬레이션 코어를 Godot과 떼어 놓고, 수치를 데이터에 두고, 고장을 부품 상태 변화로만 주입하고, 시나리오 테스트로 검증하는 구조는 에이전트가 사람 없이 스스로 확인하며 나아가기에 아주 좋은 형태입니다. 실제로 이 명세대로 M0를 끝까지 구현했고, 테스트 194개가 통과합니다(`docs/reports/M0.md`).

고칠 것은 세 종류입니다.

1. **명세 안의 모순 몇 개.** 공유 빌지 때문에 해치가 무력해지는 문제, '열쇠 아이템' 도구와 '굴러가는 공구'의 충돌, 13절 예시 시나리오가 명세 수치로 성립하지 않는 문제 등입니다. 아래 '명세 수정 제안'에 정리했습니다.
2. **임무 길이에 비해 느슨한 수치.** 공기 고장은 40분 동안 방치해도 '시야 흐림'까지밖에 가지 않습니다. 축전지 1,200Wh는 근무 임무에서 거의 위협이 되지 않습니다. 1~5장에는 수소가 생길 곳이 없습니다. 전부 데이터만 바꾸면 되는 문제이므로 M1 플레이 테스트에서 함께 맞추면 됩니다.
3. **M1 전에 사람이 정할 것.** 수리 조작 방식, Godot 실행 확인 경로, 개발용 디버그 도구 허용 여부, 자리표시 소리 여부입니다.

## 잘한 점

- **진단의 재미가 데이터 수준에서 이미 갈라져 있습니다.** 배수 펌프 하나에서 WTR-01(전류 낮음, 자갈 소리), WTR-02(전류와 온도 상승, 갈리는 소리), WTR-03(펌프는 정상인데 수위 유지)이 서로 다른 관측값으로 구별됩니다. M0 시뮬레이션에서도 세 고장이 정확히 이렇게 다르게 나옵니다.
- **'상황판은 센서가 읽은 값'이라는 원칙**이 아키텍처에 박혀 있어서, 5장의 '거짓말하는 계기'가 각본 없이 같은 구조에서 나옵니다.
- **연쇄가 실제로 동작합니다.** M0에서 리벳 누수 + 흡입구 막힘을 넣으면 각본 없이 '빌지 수위 상승 → 16분에 셀 잠김 → 염소 → 24.6분에 의식 상실'이 나오고, 해치를 닫으면 축전지가 지켜집니다.
- **수치를 한곳에 단위와 함께 모았습니다.** 검산 예시('400m, 1cm² 누수면 분당 약 24L')도 정확해서, 코드 없이 Python으로 밸런스를 미리 계산할 수 있었습니다.

## 수치 점검

M0 시뮬레이션으로 실제로 돌린 값입니다(수심 300m, 리벳 하나 integrity 0.35 = 누수 0.44L/s).

| 상황 | 결과 |
| --- | --- |
| 고장 없음, 20분 | 축전지 −6.8%(기본 부하 245W), CO2 0.04% 유지, 경보 없음 |
| 리벳 누수 + 펌프 가동, 30분 | 펌프가 따라잡아 빌지 60L 미만 유지, 축전지 −22.5% (펌프 없을 때의 두 배) |
| 리벳 누수 + 흡입구 막힘(WTR-01) | 1.9분에 수위 경보, 16.1분에 첫 셀 잠김, 18분에 염소 10ppm, 24.6분에 의식 상실 |
| 같은 조건 + 해치 닫음 | 후방 빌지 9분에 가득, 후방 바닥 침수, 축전지는 30분 내내 안전 |
