# M2 도구 모양(WP25)과 교범 그림(WP26) 지침

사용자의 요청에서 나온 두 작업 묶음이다: "교범이 너무 비직관적이다. 그림을 많이 넣어 달라. 도구도 다 똑같이 생겨서 특색이 없다." 병렬 세션 공통 지침(`docs/plans/M2-parallel-brief.md`)의 '한국어', '반드시 지킬 것' 0, 1~4, 9~12항은 여기에도 그대로 적용된다. 본선 세션이 결과를 검토하고 합친다.

## 지금 상태 (본선 97dc829 기준)

- **도구**: 도구는 17종이다(`tuning.tools`, 빈손 제외). 공구판에 걸린 모양과 바닥에 놓인 모양은 `Submarine.Tools.cs`의 `ToolMesh` 하나로 그린다. 모든 도구가 '나무 자루 상자와 색만 다른 머리 상자'로 똑같이 생겼다. 손에 든 모양(`Player/HeldItemView.cs`)은 렌치, 나무망치, 코킹 세트, 솔, 전압계 다섯 가지뿐이다. 나머지 12종은 들어도 손에 아무것도 보이지 않는다. 공구판의 윤곽도 모두 같은 네모다(`Submarine.Layout.cs`의 `BuildToolBoard`).
- **물건**: `items.json`에 44가지가 있다. 손에 든 모양은 퓨즈, 끊긴 퓨즈, 쐐기, 버팀목, 거름망 바구니 다섯 가지뿐이다.
- **교범**: `UI/MarkdownBb.cs`는 그림을 지원하지 않는다. 지금 작성 규칙도 '이미지, 링크, HTML, 코드 블록은 쓰지 않는다'이다. 교범 쪽은 '이럴 때 쓴다 / 어디에 / 무엇이 있나 / 절차 / 순서를 어기면 / 가르기' 꼴이고, 자리와 모양을 글로만 설명한다. 검토 때마다 '교범이 말하는 자리가 장면과 반대다' 같은 지적이 되풀이되었다. 예: WP20 보내기 손잡이, WP17 집게 나사, WP20 영점 나사.
- **찍기**: `tools/godot-check.sh --screenshots`가 `xvfb-run`과 `--rendering-driver opengl3`로 화면을 찍는다(`Testing/ScreenshotTour.cs`). 이 환경에서 렌더링이 된다.

## WP25 도구와 물건의 모양

브랜치 `claude/deepline-m2-tools`. 보고서 `docs/reports/m2-wp25.md`.

### 할 일

1. **도구 모형 한곳**: 새 파일 `game/scripts/Art/Kit.Tools.cs`에 `ToolModels.Build(Node3D parent, string toolId)`를 둔다. 같은 모형을 공구판, 바닥, 손 세 곳이 함께 쓴다. 손에 쥘 때의 자세(위치, 각도)는 도구마다 표로 둔다. 아트 키트의 재질(`ArtMat`)과 `MeshBuilder`를 쓴다. 모르는 도구 ID면 오류를 낸다. 대충 그린 모형으로 넘어가지 않는다.
2. **도구마다 알아볼 수 있는 실루엣**: 1930년대 해군 기관실 공구로 만든다. 멀리서 윤곽만 보아도 무엇인지 알 수 있어야 하고, 둘이 서로 닮으면 안 된다. 기준은 아래와 같다. 크기는 실물 크기로 하고, 재질과 색도 서로 다르게 한다.

   | 도구 | 모양의 핵심 |
   | --- | --- |
   | wrench 렌치 | 긴 자루 끝에 벌어진 턱과 조절 나사가 있는 멍키 렌치 |
   | mallet 나무망치 | 굵은 나무 원통 머리와 곧은 나무 자루 |
   | caulking_set 코킹 세트 | 끝이 넓게 퍼진 코킹 정과 꼰 뱃밥 다발(정은 손에, 다발은 허리에) |
   | voltmeter 전압계 | 지금 모형(베이클라이트 상자, 두 눈금, 바늘, 붉은·검은 탐침 줄)을 다듬어 쓴다 |
   | scrub_brush 솔 | 나무 등판과 짧고 빽빽한 솔, 손잡이 고리 |
   | screwdriver 드라이버 | 나무 자루, 놋쇠 고리, 납작한 긴 날 |
   | engineer_hammer 쇠망치 | 한쪽이 둥근 쇠머리(볼핀)와 나무 자루 |
   | file 줄 | 끝이 가늘어지는 쇠 줄판(빗금 무늬)과 나무 자루 |
   | scraper 긁개 | 세모 날 긁개나 넓적한 날 |
   | knife 칼 | 접이식 전기공 칼(펼친 날) |
   | rag 걸레 | 구겨진 천 뭉치(딱딱한 상자가 아님) |
   | oil_can 기름통 | 납작한 몸통, 엄지 누름판, 길고 가는 주둥이 |
   | packing_hook 패킹 갈고리 | T자 손잡이 끝에 나사처럼 꼬인 갈고리 |
   | pricker 쑤시개 바늘 | 고리 손잡이가 달린 길고 가는 바늘 |
   | stethoscope 청진기 | 기계용 청진기: 쇠막대 탐침, 나팔 귀대, 짧은 고무관 |
   | hydrometer 비중계 | 유리관 안의 뜨개와 위의 붉은 고무 공 |
   | soldering_iron 납땜인두 | 구리 끝, 쇠 막대, 나무 자루, 꼬인 전선 |

3. **손에 든 모양**: `HeldItemView`가 17종 모두를 `ToolModels`로 그린다. 쥐는 방향은 실제 쥐는 모습을 따른다(망치는 자루 끝, 드라이버는 날이 앞). 손동작 흔들림(망치질, 문지르기, 돌리기)은 그대로 둔다. 전압계 바늘 동작도 그대로 살린다.
4. **공구판 그림자 윤곽**: 공구판의 칸마다 그 도구의 실루엣을 칠한다. 옛 공구판처럼 짙은 판에 흰 칠을 한다. 도구가 빠지면 빈 윤곽이 보이고, 그 모양으로 무엇이 빠졌는지 알 수 있다. 윤곽은 모형의 바닥 투영에서 만든다. 손으로 그리지 않는다.
5. **물건 모양**: `items.json`의 44가지에 손에 든 모양과 바닥 또는 칸에 놓인 모양을 준다. 새 파일은 `game/scripts/Art/Kit.Items.cs`이고, 같은 방식(`ItemModels.Build`)으로 만든다. 새것과 헌 것(`*_worn`, `*_old`, `*_used`, `*_blown`, `*_burnt`, `*_spent`, `*_dead`, `*_flat`, `carbon_stubs`, `tube_dead`)은 눈으로 구별되어야 한다. 그을음, 닳은 모서리, 짧아진 봉, 깨진 필라멘트 같은 것이다. 이미 장비 쪽에 그린 부품(셀, 베어링, 진공관 등)이 있으면 그 모양과 맞춘다. 같은 함수를 함께 써도 된다.
6. **공구띠 그림**: 화면 아래 공구띠(`UI/Hud.cs`)의 도구 이름 옆에 작은 그림을 둔다. 그림은 `ToolModels`를 `SubViewport`로 한 번씩 찍어서 만든다. 손에 쥔 물건 이름 옆에도 같은 방식으로 그림을 둔다.
7. **확인**:
   - `tools` 확인 묶음은 모든 도구와 물건에 모형이 있는지 본다.
   - 공구판 윤곽 17개가 서로 겹치지 않고 각 칸 안에 들어가는지 본다.
   - 손에 든 모형이 화면 안에 보이는지 본다(카메라 절두체 안, 크기가 0이 아님).
   - `ScreenshotTour`에 공구판, 손에 든 도구 17장, 물건 줄 세우기 장면을 더한다. 줄 세우기 장면은 폐기함 옆 바닥이나 빈 탁자에 놓고 찍는다. 찍은 그림을 `docs/reports/img/m2-tools/`에 넣고 보고서에 붙인다.
   - 사람 확인 요청 목록(보고서 끝)에는 '도구마다 한눈에 알아볼 수 있는가'를 넣는다.
8. **건드리지 않는 것**: `data/manual`(교범 그림은 WP26이 한다), sim과 데이터의 동작. 도구와 물건의 ID, 이름, 규칙은 그대로다.

## WP26 교범 그림

브랜치 `claude/deepline-m2-figures`. 보고서 `docs/reports/m2-wp26.md`.

### 그림의 꼴

1930년대 정비 교범의 선화로 그린다: 미색 종이에 먹선, 옅은 단색 음영.

- **그림은 게임 장면에서 찍는다.** 손으로 그리거나 자리를 짐작하지 않는다. Godot에서 실제 잠수함 장면을 짓고, 시뮬레이션 상태를 맞추고(덮개를 연 모습, 고장 난 모습), 정해진 카메라로 찍는다. 찍은 뒤 먹선 처리를 한다(깊이와 법선의 가장자리 검출로 윤곽선, 명암은 세 단계 정도의 단색, 바탕은 종이색). 그러면 교범 그림과 장면이 늘 일치한다.
- **부르는 번호**: 그림 속 부품에는 동그라미 번호(①②③)와 지시선을 단다. 지시선 끝은 장면의 `Interactable`이나 이름 붙은 노드의 위치를 화면에 투영해서 정한다. 번호의 뜻은 그림 바로 아래 교범 글에 적는다. 보통은 그 쪽 '무엇이 있나' 표의 순서와 맞춘다.
- **그림 속 글자**: 그림 안에는 한국어 글을 새로 쓰지 않는다. 번호와 장비 이름만 넣고, 장비 이름은 `data/text/ko`의 이름 키에서 가져온다. 설명은 모두 마크다운에 둔다. 그래야 한국어 검토가 글만 보고 끝난다.
- **도식**: 장면에서 찍기 어려운 것은 Godot 2D로 같은 먹선 꼴의 도식을 그린다.
  - 구역 배치도: 위에서 본 평면도. 장비 자리는 배치(`Submarine.Layout.cs`)의 좌표에서 가져온다.
  - 계통도: 배전반 C1~C8에서 장비까지는 `circuits.json`과 `devices.json`, 배수와 밸러스트 배관과 흡입 선택기는 `parts`에서 가져온다.
  - 조이는 순서도: 볼트 번호와 순서. `sequenceFrom` 데이터에서 그린다.
  - 손동작 화살표: 도는 방향과 끄는 방향.
  - 계기 읽는 법: 전압계의 두 눈금, 비중계, 경사계.
  - 계산 도구 풀이 예: 계산자, 계산 도표.
  
  자료에서 그리는 도식은 데이터가 바뀌면 따라 바뀐다.
- **크기와 파일**: 폭 960픽셀 안팎에 16색 이하의 팔레트 PNG로 한다. 한 장 평균 80KB 안, 모두 합쳐 8MB 안. 파일은 `data/manual/fig/<쪽 번호>-<영문 이름>.png`(예: `30-bearing-cover.png`)에 둔다. 그림 정의(카메라, 시뮬레이션 상태, 부르는 번호의 대상, 도식 종류)는 `data/manual/fig/figures.json`에 두고 만들기 코드가 읽는다. 다시 만들기는 `tools/make-figures.sh`(xvfb-run, opengl3)로 한다.

### 교범에 넣는 법

- 마크다운 문법은 한 줄에 `![그림 30-1. 배수 펌프의 베어링 뚜껑과 볼트 번호](fig/30-bearing-cover.png)` 하나다. 번호는 '그림 <쪽>-<차례>'이고, 본문은 '(그림 30-1)'로 가리킨다. 그림 설명은 교범 문체로 짧게 쓴다.
- `MarkdownBb`와 `ManualOverlay`가 그림을 그린다.
  - 데이터 폴더의 PNG를 실행 중에 읽어서(`Image.LoadFromFile`, `ImageTexture`) `RichTextLabel.AddImage`로 넣는다.
  - 설명은 그림 아래 작은 글씨로 단다.
  - 그림을 누르면 크게 본다.
  - 교범 폭에 맞춰 줄이되, 실제 크기보다 키우지 않는다.
- `sim/Manual/ManualText.cs`는 그림 줄을 그대로 넘긴다. 자리표시자는 설명 안에서도 쓸 수 있다.
- 교범 작성 규칙(`MarkdownBb` 머리 주석, 설계서의 교범 규칙)을 '그림은 `![설명](fig/…)` 한 줄로 넣는다'로 고친다.
- 그림을 넣을 자리는 아래와 같다. 모든 쪽에 넣고, 쪽마다 적어도 셋이다.

  | 쪽 | 그림 |
  | --- | --- |
  | 고장 쪽 | '어디에': 배치도 위의 자리 표시와 그 장비를 서서 본 모습<br>'무엇이 있나': 번호를 단 부품 그림<br>절차마다 순서 그림: 그 절차를 실제로 해 보며 중요한 단계마다 작업 시점에서 찍은 칸을 이어 붙인 띠. 칸의 번호는 절차 표의 단계 번호와 같다<br>'가르기'의 정상 대 고장 비교(그을린 퓨즈, 닳은 브러시, 막힌 거름망 같은 것) |
  | 01 개요 | 구역 배치도와 계통도 넷(전기, 배수와 밸러스트, 공기, 증기) |
  | 02 상황판 | 번호를 단 상황판 정면, 표시등 세 색의 예, 계기와 기준 짝 |
  | 06 손과 도구 | 공구판 전체(WP25가 들어간 뒤), 도구마다 하는 일, 손동작 화살표 |

  | 12 침수 대응 | 구역별 물이 들어오는 자리 |

  진단 표 쪽(03, 04, 05)에는 증상 단서(표시등, 계기 바늘)의 작은 그림을 표 앞에 모아 둔다.
- **순서 그림 만들기**: `ProcedureRunner.ExpandWithBelt`로 절차를 펼친다. 자동 플레이어처럼 `Perform`으로 하나씩 하고, 보이는 상태가 바뀌는 단계마다 그 장비의 작업 시점 카메라로 찍는다. 손에 든 도구도 함께 보이게 한다. 찍는 대상 단계는 `figures.json`에 단계 번호로 적는다. 칸에는 그 단계 번호를 단다.

### 순서와 범위

1. 그림 길: 렌더러(`MarkdownBb`, `ManualOverlay`), 그림 만들기 모드, 먹선 처리, 부르는 번호, 도식 그리개, `figures.json`, 시험.
2. 일반 쪽(01, 02, 06~12)과 지금 본선에 있는 고장 쪽(20, 21, 23, 25, 26, 27, 29, 30, 33, 34, 36, 38, 39, 42, 43, 44, 45). 06쪽의 도구 그림은 WP25가 본선에 들어간 뒤 다시 찍는다(본선 세션이 알린다).
3. 2차 고장 쪽(13, 22, 24, 28, 31, 32, 35, 37, 40, 41)은 WP17~20이 본선에 들어간 뒤 한다. 본선 세션이 알린다. 그때까지는 그 쪽의 글에 손대지 않는다. 다른 세션이 같은 쪽을 고치고 있기 때문이다.

### 확인

- `sim.tests/ManualTests.cs`:
  - 모든 `![…](fig/…)`의 파일이 있다.
  - 모든 그림이 `figures.json`에 있고, 꼭 한 쪽에서만 쓰인다.
  - 번호 '그림 <쪽>-<차례>'가 쪽 번호와 맞고 차례가 빠지지 않는다.
  - 크기 한도를 지킨다.
- 교범 그림 줄을 넣어 M1 쪽 렌더가 바뀌면 `sim.tests/fixtures/manual-m1/`의 그 쪽 스냅숏을 다시 만들고 보고서에 적는다.
- Godot `figures` 확인 묶음: 모든 그림 정의를 헤드리스로 다시 계산한다.
  - 카메라가 장면 안에 있는지 본다.
  - 부르는 번호의 대상이 있고, 투영한 자리가 그림 틀 안이며, 다른 물체에 가려지지 않는지 본다(광선 검사).
  - 순서 그림의 절차가 끝까지 해가 없이 도는지 본다.
  - 배치나 장비가 옮겨져 그림 정의가 낡으면 이 묶음이 실패한다.
- 교범 덮개(`AutoPlayer.CheckOverlays`)에서 그림이 든 쪽을 펴 보고, 그림이 실제로 그려졌는지(텍스처 크기가 0이 아님) 본다.
- 그림을 다 만든 뒤 사람 확인용으로 그림이 든 교범 쪽을 몇 장 찍어 `docs/reports/img/m2-figures/`에 넣는다.

### 앞으로의 규칙

이 WP가 들어간 뒤로 새 교범 쪽을 쓰는 작업 묶음은 같은 길로 그림을 함께 넣는다. 이 규칙은 본선이 `M2-parallel-brief.md`에 더한다.
