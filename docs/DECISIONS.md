# 결정 기록

SPEC 0절 규칙 6에 따라, 명세에 없거나 명세와 다르게 정한 것을 기록한다. 사람에게 확인을 요청한 항목은 '확인 요청'으로 표시했다(`docs/REVIEW.md`의 질문 번호).

## 2026-10-27 · 사람 결정

`docs/REVIEW.md`의 질문에 대한 답. SPEC.md에도 반영했다(15절 표와 해당 절).

- **질문 1 빌지와 해치**: 추천대로. 빌지를 해치 기준 두 칸으로 나누고, 해치를 닫으면 빌지도 갈린다 (M0 구현 그대로).
- **질문 2 근무 파트의 수소**: 추천대로. 잠긴 셀에서 수소가 나온다 (M0 구현 그대로).
- **질문 3 수리 방식**: **자유형.** 화면에 단계 안내 없이 물체를 직접 조작하고, 매뉴얼은 언제든 **Tab** 키로 펼친다. 매뉴얼은 그것만 보고 진단하고 고칠 수 있을 만큼 자세해야 한다. 그래서 SPEC 7절의 조작표를 바꿨다: Tab = 매뉴얼, N = 메모장 (원래 Tab = 메모장, B = 매뉴얼).
- **질문 4 Godot 실행 확인**: 추천대로. 클라우드 환경에서 Godot 릴리스를 받을 수 있게 되어, 에이전트가 Godot 4.7.2 .NET 헤드리스로 직접 확인한다. 조작감은 사람이 PC에서 본다.
- **질문 5 개발용 디버그 도구**: 추천대로. 디버그 빌드 한정으로 허용 (SPEC 14절 예외).
- **질문 6 M1 소리**: 추천대로. 자리표시 합성음을 넣고 음색은 M5에서 판단.
- **나중에 정할 질문들**: 모두 추천 기본값으로 진행한다 (SPEC 15절 표). 임무 시간은 실제 시간, 공기와 축전지 수치는 M1 플레이 테스트에서 조정, 임무 중 저장 없음, 도구는 들고 다니는 물건(M2), 한국어 기본과 OFL 폰트.
- **M0 승인**: `m0` 태그를 붙인다.
- **진행 속도 (M1 이후)**: 마일스톤마다 멈추지 않고 계속 진행한다. 플레이 테스트는 M2, M4, M7 끝에 몰아서 한다. 다른 일에 기대지 않는 작업(M5 아트 키트, 사운드 합성기, 이야기 글 초안)은 별도 클라우드 세션이 각자의 브랜치에서 미리 만들고, 본선 브랜치에 합친다. 결정할 거리는 추천 기본값으로 진행하고 기록한다.
- **한국어 문체 (사람의 지시)**: 모든 한국어는 자연스러워야 한다. 교범은 정비 교범다운 딱딱한 설명문체(‘~다’ 평서문, ‘~한다’ 지시, 수사와 구어체 없이 짧고 정확하게)로 쓴다. 화면 문구는 몸이 느낀 일을 짧은 평서문 한 줄로 쓴다. 용어는 공구판, 공구띠로 통일한다.

## 2026-10-27 · M0

### 저장소와 도구

- **저장소 루트를 SPEC 2절의 `deep-line/`으로 본다.** 하위 폴더를 하나 더 만들지 않는다. 이유: 저장소가 이 게임 하나만 담는다.
- **대상 프레임워크는 net8.0, 언어 C# 12.** `Directory.Build.props`에서 한 줄로 바꿀 수 있다. 이유: Godot 4.7.2 .NET의 GodotSharp가 net8.0을 대상으로 한다(NuGet 확인). .NET 8 지원은 2026-11-10에 끝나지만 Godot 템플릿이 올라갈 때 함께 올린다.
- **Godot 버전은 4.7.2 stable(.NET)로 고정한다.** 에디터와 Godot.NET.Sdk 버전을 맞춘다. 4.8은 안정판이 나오기 전까지 쓰지 않는다.
- **결정론을 깨는 API를 빌드 오류로 막는다.** `sim/BannedSymbols.txt`(Microsoft.CodeAnalysis.BannedApiAnalyzers 3.3.4): System.Random, 실제 시각, Stopwatch, Math.Pow/Exp/Log/삼각함수, MathF, string/object.GetHashCode, HashCode, Parallel, ThreadPool. 이유: 0절 규칙 3. 초월 함수는 플랫폼마다 마지막 비트가 다를 수 있다. `Math.Sqrt`는 IEEE 754가 정확한 반올림을 보장하므로 허용한다.
- **곡선은 데이터의 구간 선형 표로 정의한다** (예: 축전지 f(charge), 베어링 wear → 저항).
- **개발 도구 `tools/DeepLine.SimCli`를 추가했다.** 시나리오를 돌려 시계열 CSV를 뽑는다. SPEC 2절 구조에 없지만 사람 검토를 돕는다. 게임 화면의 HUD가 아니므로 14절과 무관하다.

### 데이터

- **파일 이름은 SPEC 8절 표를 따르고 `circuits.json`을 더했다.** 회로 이름, 퓨즈 정격, 시작 시 스위치 상태. SPEC 2절의 data 목록(parts, systems, gimmicks …)과 8절 표가 서로 달라서 8절을 기준으로 삼았다.
- **모르는 JSON 필드는 오류로 처리한다.** 오타를 바로 잡기 위해서다. JSON 주석과 끝 쉼표는 허용한다.
- **faults.json에 `effects` 식을 두지 않는다.** 고장은 부품 상태 값(`set`)과 상태 단계(`state`)만 바꾸고, 증상은 계통 코드가 그 값을 읽어 만든다. SPEC 8절이 허용한 대안이다. 이유: 같은 물리 상태가 고장 주입이 아닌 경로(예: M4 부착물 기믹의 흡입구 막힘)로 생겨도 같은 증상이 나와야 한다. 식 해석기도 필요 없어진다.
- **누수 지점도 부품이다.** hull.json의 지점마다 부품을 만들고, 부품 종류는 지점의 kind(rivet, viewport, shaft_packing, hull_valve, chamber_door)다. HUL-01은 rivet에만 주입된다.
- **누수 지점 20곳의 배치와 최대 면적 (가안).** 리벳 12곳은 전방·중앙·후방에 4곳씩 3cm², 현창 2곳 전방 2cm², 축 패킹 후방 4cm², 선체 밸브 4곳(전방 1, 중앙 2, 후방 1) 5cm², 챔버 바깥 문 6cm². 설계 수심은 모두 600m. 챔버 문 누수는 실내가 아니라 챔버 물로 들어간다.
- **HUL-01 주입값은 integrity 0.35.** 수심 300m에서 0.44L/s로, 펌프(2.0L/s)가 따라잡지만 펌프를 켜야 하는 크기다.

### 시간

- **고정 틱 20Hz, 틱 T의 상태는 Step()을 T번 한 뒤의 상태다.** 명령은 Apply()로 대기열에 들어가 다음 Step()의 처음에 실행된다. 고장 주입(`Simulation.Inject`)은 틱 사이에 바로 적용된다.
- **SimWorld.Step()의 계통 순서**: 명령 → 전기(전압, 회로, 장비, 퓨즈) → 방전 → 열 → 마모 → 선체 → 침수 → 공기 → 소음 → 폭발 판정 → 상황판 → 몸 상태 → 무작위 고장 → 부품 상태 사건. 순서를 바꾸면 기준 해시를 다시 만들어야 한다.

### 전력과 배전반

- **버스 전압 V = (1/6) × Σ(활성 셀의 f(charge) × health 배율).** health 배율 = 0.5 + 0.5 × health. 점퍼한 셀은 빼고, 점퍼하지 않은 죽은 셀(health < 0.05 또는 파손)이 있으면 V에 0.3을 곱한다(큰 내부 저항). 이유: SPEC 식에는 health가 없어 PWR-01의 '전압계 하락'이 나오지 않고, 점퍼가 식에서 의미가 없다. 셀이 모두 같으면 SPEC 식과 같다.
- **셀 용량 = 200Wh × health.** 직렬이라 활성 셀마다 같은 에너지가 빠지고, 열화 셀(용량이 작음)의 charge가 먼저 떨어진다. 비중계 증상의 원천이다.
- **셀 발열 = 셀 전력 × 0.05 × (1 + (1 − health) × 10)**, 냉각 1W/°C, 열용량 1000J/°C. 열화 셀이 '뜨거운 셀'이 된다.
- **장비 부하 종류를 둔다.** 저항성(조명, 점화기, 상황판, 청음기, 탐조등, 납땜인두): P = P₀·V², I = P₀·V. 전동기(나머지): P = P₀·부하율, I = P/V (SPEC 식). 이유: SPEC의 I = P/V를 모든 장비에 쓰면 전압 하락만으로 퓨즈가 끊길 수 있다.
- **장비별 최소 전압 (가안)**: 탐조등 0.85, 자이로 0.8, 윈치 0.75, 추진·소나·항법 계산기 0.7, 펌프·청음기·사이펀·납땜인두 0.6, 팬·점화기 0.5, 상황판 0.4, 조명 0.1.
- **퓨즈 정격은 '정상 부하의 최악 전류 × 1.1' 이상이어야 한다는 데이터 검증 규칙**을 둔다. 퓨즈는 부하 고장(베어링, 누전)에서만 끊긴다. 정격(가안): C1 50, C2 150, C3 560, C4 680, C5 100, C6 920, C7 100, C8 1300. 단위는 정규화 전류(공칭 전압에서의 W).
- **퓨즈가 끊긴 틱부터 회로와 장비가 멈춘 것으로 보인다.** 그 틱의 전력은 소비하지 않은 것으로 친다(0.05초분).
- **누전**: 분기함(회로마다 `junction.Cx`)의 습기가 0.6을 넘으면 누설 전류 = (습기 − 0.6)/0.4 × 0.7 × 퓨즈 정격 × V. 회로 스위치를 내리면 멈춘다('해당 분기 차단'). 정격 비율로 둔 이유: 어느 회로든 부하가 걸리면 같은 퓨즈가 반복해서 끊기고, 부하가 없으면 퓨즈는 버티되 전력이 새게 하려고. 습기의 원천(침수, 증기 누설)은 M2.
- **시작 시 회로 상태**: C3(배수)와 C7(공구)은 꺼져 있고 나머지는 켜져 있다. 펌프 장비 자체는 켜져 있어서 C3 스위치가 곧 펌프 스위치다(SPEC 13절 예시의 `switch.C3.on`과 맞춤). 펌프는 빌지가 비어도 돌면 전력을 쓴다(부유 스위치 없음).

### 침수

- **빌지를 해치 기준 두 칸으로 나눴다 (확인 요청, 질문 1).** 전중 빌지 360L(전방·중앙 아래, 축전지, 수동 펌프), 후방 빌지 240L(후방 아래, 전동 펌프 흡입구). 해치가 열려 있으면 두 칸이 같은 비율로 맞춰지고(초당 0.5), 닫으면 바닥 위 물과 빌지 칸 모두 해치 양쪽이 갈린다. 축전지는 전중 빌지 240L(합계 400L와 같은 비율)에서 잠기기 시작해 360L에서 6셀이 모두 잠긴다. 이유: SPEC의 공유 빌지로는 해치가 빌지가 찰 때까지 효과가 없어 DESIGN의 '해치를 닫을지가 첫 판단'이 성립하지 않는다. tuning.json의 `water.hatch.bilges`를 비우면 칸이 늘 이어진다.
- **물 경로**: 누수 → 그 구역 아래 빌지 칸(넘치면 그 구역 바닥 위) → 펌프 → 빌지 칸 맞춤 → 바닥 위 물이 빌지로 빠짐(초당 5L) → 이웃 구역 바닥 위 물이 퍼짐(초당 0.2).
- **수동 펌프는 전중 빌지에서 한 번에 1.5L.** 위치는 중앙 구역(가안).
- **구역 바닥 면적은 SPEC대로 8m².** 검토에서 '물이 차오르는 것이 눈에 잘 안 보인다'는 지적이 있어 M1에서 다시 본다.
- **침몰 실패는 바닥 위 물 합계 6,000L 초과로 대신한다.** M2 부력 모델 전까지의 대리 기준.

### 선체

- **응급 패치는 부품 상태 값 `patchFactor`(누수 면적 배율)와 `patchDurability`로 표현한다.** 내구도는 초당 0.0005 × s씩 줄고 0이 되면 원래 누수로 돌아간다(PatchFailed 사건). M0에는 패치를 붙이는 수리가 없어서 시나리오가 값을 직접 넣어 시험한다.
- **선체 붕괴**: 어느 지점이든 응력 s ≥ 1.5이면 임무 실패(가안).
- **구역 경고등**은 상황판과 별개로 축전지 직결 비상 급전으로 켜진다(전압이 조금이라도 있으면). 그 구역 누수 유입이 0.05L/s(tuning.hull.zoneAlarmInflowLps) 이상이거나 바닥 위 물이 1L를 넘으면 켜진다.

### 공기

- **실내 공기는 한 덩어리다.** 팬이 염소와 수소를 줄이는 것은 게임 추상화다(밀폐 선내에서 실제로는 갈 곳이 없다).
- **흡수통은 팬이 돌 때만, 바닥값 0.04%까지만 흡수한다.** 흡수량 = min(0.15%/분, CO2 − 0.04). 6%분을 흡수하면 포화되고 AIR-02가 저절로 주입된다.
- **잠긴 셀에서 수소가 나온다 (확인 요청, 질문 2).** 셀당 +0.1%/분, 팬이 돌면 분당 20%씩 줄어든다. 염소는 셀당 +3ppm/분, 팬이 분당 20%씩 줄인다. 이 값이면 '셀 1개 + 팬 정상 = 기침 수준(15ppm)', '4셀 이상 = 팬이 돌아도 치명(60ppm)'이다.
- **산소 양초**: 점화기(C2)가 돌 때만 불을 붙일 수 있고, 한 번에 하나, 재고 4개(가안).
- **실내 부피 30m³는 아직 쓰이지 않는다.** 변화율이 %/분으로 주어져 있어서다.
- **공기 변화율은 SPEC 값을 그대로 쓴다.** 검토에서 근무 임무 길이에 비해 느리다는 지적이 있다(`docs/REVIEW.md`). M1 플레이 테스트에서 맞춘다.

### 열과 마모

- **장비 발열 = 소비 전력 × heatFactor × (1 + 장비 부품의 최대 wear).** 과열 임계를 넘으면 그 장비 부품의 wear가 3배로 쌓인다. 펌프는 95°C에서 과열 정지하고 50°C에서 다시 돈다.
- **wear 증가 = 기본 속도 × dt × 부하율 × 환경(과열 3배) × 품질 계수(정품 1, 응급 4).** wear가 고장 임계(0.8)를 넘으면 부품의 `wearFault`(펌프 베어링은 WTR-02, 팬 모터는 AIR-01)를 주입한다.
- **부품 상태 값의 일부는 wear에서 저절로 나온다** (`wearCurves`). 베어링 저항 drag = 곡선(wear): 0.5 → 0, 0.8 → 0.4, 1.0 → 1.0. 펌프 부하율 = 1 − 0.6 × 흡입구 막힘 + 1.0 × drag. WTR-02 주입은 wear를 0.85로 올린다. 이유: 고장 매개변수와 wear가 따로 놀지 않게 한다.
- **부품 상태 = max(wear 기준 상태, 주입된 고장의 상태 하한).** 주입된 하한은 수리(M1)가 지운다.

### 소음

- **누적 소음은 dA/dt = (gain × N − A) / τ, gain 1, τ 90초.** 이유: SPEC 식 dA/dt = N − 0.1A는 시간 단위가 없다. 초로 읽으면 시정수 10초라 숨죽이기에 대가가 없고, 분으로 읽으면 수리 소음이 무의미하다. 정규화하면 A가 N과 같은 단위가 되어 소리 사냥꾼 임계값을 N 단위로 읽을 수 있다. τ는 M4에서 사람과 맞춘다.
- **현재 소음 N은 0~100으로 자른다.** 스로틀 장비(추진)는 소음 × 스로틀.
- **행동 소음은 크기와 지속 시간을 가진다** (tuning.json `noise.actions`). 크기는 SPEC 값(퓨즈 교체 2, 렌치 3, 줄질 10, 수동 펌프 25, 역세척 35, 망치 40, 코킹 45), 지속 시간은 가안.

### 상황판과 몸 상태

- **M0의 센서는 진짜 값을 그대로 통과시키는 이상적인 센서다.** 상황판 판단은 `PanelSystem.Sense()` 한 곳을 거치므로 M2의 센서 고장(SNS-01, 02, 05)은 거기에 들어간다. Snapshot의 `Panel`이 센서 값이고, Godot 층의 상황판 표현은 반드시 이것을 쓴다.
- **표시등 판정 (가안)**: 동력은 V < 0.88 주의, < 0.7 고장, 셀 28°C 초과 주의. 배전반은 켜진 회로의 퓨즈 단선 고장, 정격 90% 초과 주의. 공기는 SPEC 임계값과 수소 2%/3.5%. 배수는 빌지 합계 60L 주의, 300L 고장, 펌프 60°C 초과 주의. 선체는 구역 경고등이 켜지면 주의, 바닥 위 물이 있으면 고장. 감각·항법·케이블은 그 회로에서 켜 둔 장비가 안 돌면 주의(회로가 죽었으면 고장).
- **경보 벨은 표시등이 더 나빠질 때마다 울린다** (AlarmBell 사건).
- **의식 상실(CO2 8%, O2 11%, 염소 60ppm)은 즉시 임무 실패다.** 감전의 '체력 손상'은 M1에서 정한다.
- **실패 후에도 시뮬레이션은 계속 진행한다.** 재시작은 표현 층이 `Simulation.Reset()`으로 한다.

### 명령

- **명령은 원자 손동작 단위의 문자열이다.** M0 어휘: `switch.<회로>.on|off`, `device.<장비>.on|off`, `hatch.close|open`, `handpump.stroke`, `cell.<n>.jumper|unjumper`, `propulsion.set`(value = 스로틀), `sonar.ping`, `candle.light`, `noise.emit`(value = 크기, value2 = 초). 문법이 틀리면 Apply()에서 예외, 게임 상태 때문에 못 하면 CommandRejected 사건.
- **수리 판정은 '물체 상태 + 행동별 전제 조건'으로 한다 (확인 요청, 질문 3).** M1에서 구현한다. procedures.json은 매뉴얼, 자동 플레이어, 숨은 결함 판정의 기준으로 쓴다.

### 무작위 고장

- **발생률 = 시간당 기본값 × (1 + 수심/1000m) × (1 + 4 × wear)**, 1초마다 (고장 ID, 부품 ID) 서수 순서로 추첨한다. 고장별 하위 난수 스트림(`faults.random`)을 쓰므로 나중에 다른 난수 소비자가 생겨도 기존 결과가 밀리지 않는다. 시나리오와 임무가 `randomFaults: true`로 켤 때만 동작한다.

### 테스트

- **단위 테스트의 기대값은 data의 튜닝 값에서 계산한다.** 튜닝을 바꿔도 규칙 검증은 깨지지 않는다.
- **시나리오 테스트(`sim.tests/scenarios/`)는 실제 data로 돌리고, 방향과 순서와 넉넉한 시간 상한을 검사한다.** SPEC 13절 형식을 넓혔다: `atTick`, `always`, `never`, `fromTick`/`toTick`, `ordered`, `setup`, 주입별 `set`/`state`. assert 문법은 `sim/Faults/Assertion.cs` 주석, 관측값 경로 목록은 `sim/Core/SimQuery.cs`.
- **SPEC 13절의 예시 시나리오(HUL-03)는 쓰지 않았다.** HUL-03은 M2 범위이고, 명세 수치로 성립하지 않는다(`docs/REVIEW.md`). 같은 연쇄(누수 → 펌프 → 축전지)는 시나리오 09가 HUL-01로 검사한다.
- **리플레이 테스트는 두 층이다.** 같은 프로세스에서 틱마다 해시 비교, 그리고 저장소의 기준 해시(`sim.tests/fixtures/golden-hashes.json`)와 비교. 기준 해시는 시나리오마다 따로 있고 1분(1200틱) 간격의 해시 목록이라, 갈리면 어느 구간에서 갈렸는지 보인다. 고정 데이터 사본(`sim.tests/fixtures/golden-data/`)으로 만들어서 data 튜닝과 무관하다. 무작위 고장 발생률을 크게 올린 리플레이(`replay-random`)도 포함한다. 규칙을 일부러 바꾸면 `DEEPLINE_REGEN_GOLDEN=1 dotnet test`로 다시 만들고, 바뀐 키를 커밋 메시지에 적는다. 다른 OS에서 이 테스트가 실패하면 플랫폼 간 결정론이 깨진 것이다. 기준 해시는 변경 감지기일 뿐이고, 규칙마다 의미 테스트를 따로 둔다.
- **성능 테스트는 Debug 빌드에서 틱당 1ms 미만을 확인한다** (측정값 약 18µs).
- **시나리오 실행기는 틀린 시나리오를 거부한다.** 기대값의 창이 뒤집혔거나 실행 길이를 넘으면, 또는 명령과 주입이 실행 범위 밖이면 InvalidDataException. 한 번도 평가되지 않은 기대값은 실패다.

## 2026-10-27 · M0 코드 리뷰 반영

4개 관점(결정론, 명세 적합성, 로직 버그, 테스트 품질) 리뷰와 반박 검증에서 확인된 결함을 고치며 정한 것.

- **수치의 기본값을 코드에 두지 않는다.** tuning과 정의 클래스의 속성은 `[Optional]`이 없으면 JSON에 반드시 있어야 하고, 빠지면 로드가 실패한다. 선택 속성이 빠지면 '그 기능 없음'이다(예: `heatFactor`가 없으면 열이 나지 않고, `overheatC`가 없으면 과열하지 않는다). 이유: 코드 기본값과 데이터 값이 달라서 키가 빠지면 다른 수치가 조용히 쓰였다.
- **코드가 이름으로 붙는 데이터는 `sim/Data/Bindings.cs` 한 곳에 모으고 검증한다.** 장비 ID, 부품 ID와 그 상태 값, 부품 종류별 상태 값, 코드가 직접 주입하는 고장(ELC-01은 fuse에 blown = 1, AIR-02는 canister에 saturation = 1).
- **사전의 순서는 언제나 서수 비교다.** JSON 읽기는 문화권 비교자로 사전을 만들기 때문에 GameData가 서수 비교로 다시 담는다. 부품 상태 값의 순서가 해시와 저장 형식에 들어가므로, 플레이어 로캘마다 해시가 달라지는 것을 막는다.
- **빌지 칸의 순서와 이웃 관계는 칸이 덮는 구역의 앞뒤 순서로 정한다.** 칸은 이어진 구역을 덮어야 하고, 해치는 이웃한 두 칸 사이에 있어야 한다(검증).
- **빈 셀(charge 0)은 에너지를 내지 않고, 그 몫은 다른 활성 셀이 진다.** 소비 전력과 방전량은 언제나 같다. 빈 셀은 발열하지 않는다. 빈 셀은 '죽은 셀'(health 기준)이 아니라서 전압 ×0.3 감쇠는 없고, f(0) = 0이라 전압 기여만 사라진다. 그래서 빈 셀을 점퍼해도 전압은 그대로다.
- **고장 주입은 나빠지는 방향으로만 적용한다.** 고장의 set 값이 부품의 처음 값보다 작으면(integrity, health) 지금 값과의 최솟값, 크면(clog, moisture, stuck) 최댓값. 이미 더 나쁜 부품에 다시 주입해도 나아지지 않는다. 시나리오와 디버그 도구의 `set` 덮어쓰기는 그대로 적용한다. wear가 스스로 임계를 넘어 생긴 고장에는 고장의 wear 하한(WTR-02의 0.85)을 적용하지 않는다(한 틱에 wear가 뛰지 않게).
- **퓨즈가 어떤 경로로든 통전 중에 끊기면 FuseBlown 사건과 불꽃이 난다.** 과전류, 주입, 무작위 고장 모두 같다. 꺼진 회로의 퓨즈가 끊기면 불꽃이 없다. 폭발은 임무가 진행 중일 때 한 번만 난다.
- **퓨즈 정격 검증은 새 부품(부하율 1) 기준이다.** 마모가 Warning 단계에서 이미 부하를 올리는 부품(펌프 베어링)은 저전압과 겹치면 고장이 주입되기 전에도 퓨즈를 끊을 수 있다. 베어링 마모는 진행 중인 부하 고장이라 의도한 동작으로 본다.
- **펄스 장비는 정수 틱으로 돈다.** 1초 핑 = 20틱. 부동소수 잔차로 한 틱이 빠지던 문제를 없앴다.
- **수동 펌프 한 번은 1.2초 걸린다** (`water.handPumpStrokeSeconds`). 그 사이에 들어온 펌질은 CommandRejected. 이유: 코어가 판정한다는 원칙(3절). 표현 층이나 자동 플레이어가 명령을 연발해도 전동 펌프보다 빨리 퍼낼 수 없다.
- **명령 값은 유한한 수여야 하고, `noise.emit`은 최대 60초다** (`noise.maxEmitSeconds`).
- **상황판 표시등과 계기, 구역 경고등은 모두 `SensorReadings` 한 벌만 읽는다** (`PanelSystem.Sense`). 회로의 통전과 퓨즈와 전류, 구역별 유입 감지와 바닥 수위, 장비 가동까지 센서 값이다. M2의 센서 고장은 여기에만 넣으면 모든 표시에 반영된다. '그 회로의 장비가 안 돌면 주의'인 표시등과 회로의 대응은 `panel.circuitLamps`에 둔다.
- **상황판에 배수량 계기(`PumpFlow`)를 더했다.** WTR-01의 상황판 단서 '배수량 0'을 직접 보여준다.
- **Snapshot에 현장 단서용 값을 더했다.** 회로별 누설 전류와 분기함 습기(결로, 감전 위험), 장비 과열 여부(연기, 냄새), 펌프 총 배출량(순 배출량과의 차이가 역류 소리). 감전 사건과 '분기함 만지기' 같은 명령은 M1 상호작용에서 넣는다.
- **저장본에 시드, 시작 설정, 아직 꺼내지 않은 사건을 넣는다.** RestoreState 뒤 Reset()은 저장한 임무의 시작으로 돌아간다. 시작 설정은 Load할 때 복사해 두어 호출자가 나중에 고쳐도 영향이 없다. 아직 꺼내지 않은 사건은 결과에 영향이 없으므로 해시에서는 뺀다.
- **결정론 금지 목록을 넓혔다.** double의 초월 함수 정적 메서드, Math.Log(x, b)/Log2/Atan/Asin/Acos/Cbrt/쌍곡 함수, ReciprocalEstimate, TimeProvider, Guid.NewGuid, Task, Thread, Vector&lt;T&gt;.
- **공유 정적 목록(구역, 표시등 이름)은 읽기 전용이다.** Snapshot은 내부 배열을 내보내지 않는다. GameData의 정의 객체는 아직 공개 setter가 있다(테스트가 발생률을 바꾸는 데 쓴다). 한 데이터를 여러 시뮬레이션이 같이 쓸 때 도중에 고치지 않는다.

### 손 수리 (SPEC 6절)

- **명령 하나가 손동작 하나다.** 볼트 하나 풀기, 망치 한 번, 솔질 한 번. 리플레이와 자동 플레이어가 같은 단위를 쓴다. 문법은 `sim/Core/Command.cs`.
- **물리적으로 할 수 없는 동작은 거부하고, 할 수는 있지만 위험한 동작은 위험을 일으킨 뒤 진행한다.** SPEC 6절의 '전제 조건을 어기면 거부하지 않고 hazard'를 이렇게 읽었다. 조여진 볼트가 누르는 덮개는 열리지 않고(`bolts_tight`), 살아 있는 소켓의 퓨즈는 뽑히지만 감전된다. 거부는 `CommandRejected` 사건과 사유 코드로 알린다.
- **손은 도구 하나(빈손 포함)와 물건 하나를 든다.** 도구는 1~6 키로 바로 바꿔 든다. 도구를 선내에서 들고 다니는 물건으로 만드는 것은 M2(REVIEW '나중에 정할 질문').
- **위험은 감전과 끼임 두 가지.** 감전은 숨은 체력 0.25를 깎고 2.5초 손을 못 쓰게 한다. 끼임은 0.15와 1.5초. 체력은 분당 0.02 회복하고, 0이 되면 '쓰러짐'(incapacitated)으로 임무 실패. 체력은 숫자로 보이지 않고 화면이 어두워지고 빛이 바래는 것으로만 보인다.
- **고장 상태는 원인인 부품을 고쳤을 때만 지운다.** 다른 부품을 손보면 그 부품만 새것이 되고 증상은 남는다.
- **거름망의 숨은 결함**: 볼트가 하나 풀려 있을 때마다 흡입 쪽으로 공기가 새어 배수량이 25%씩 준다(`repair.looseBoltAirLeak`). 바구니 없이 펌프를 돌리면 베어링이 5배 빨리 닳는다.
- **조이는 순서에 따른 숨은 결함은 M2부터** (HUL-02 현창 밀봉의 대각 순서). M1의 숨은 결함은 위의 풀린 볼트와 빠진 바구니뿐이고, procedures.json을 숨은 결함의 기준 순서로 쓰는 것도 M2에서 시작한다.
- **리벳 응급 막기**: 쐐기 3번(유입 35%, 패치 내구도 0.5), 버팀목(10%, 1.0), 품질 '응급'. **코킹** 8번이면 새것처럼 메워지는(integrity 1.0) 정식 수리가 되고 응급 패치를 걷어 낸다. 처음에는 0.9로 했으나 남는 미세 누수가 쉿 소리와 물줄기를 남겨 교범의 '끝난 뒤 확인'과 어긋나서 바꿨다(M1 리뷰). 코킹 진행은 이음새에 남아서 나눠 쳐도 된다.
- **분기함 만지기(습기에 의한 감전)는 M2로 미룬다.** 누전(ELC-03)의 수리와 함께 넣는다. 교범에는 결로를 눈으로 보는 단서만 적었다.

### 임무

- **임무 스크립트**: `data/missions/*.json`에 시드, 시작 설정, 정해진 시각의 고장, 성공 assert와 유지 시간, 제한 시간을 둔다. 성공 assert가 `holdSeconds`(0보다 커야 함) 동안 계속 참이면 성공, 제한 시간을 넘기면 실패. 진행 상태는 상태 해시와 저장에 들어간다. **성공과 실패는 최종이다**: 끝난 뒤에는 어떤 실패도 결과를 바꾸지 않고, 게임은 결과 화면에서 시간을 멈춘다.
- **m1-crisis**: 수심 300m, 흡입구 막힘(0초) → 후방 리벳 09 누수(20초) → C3 퓨즈 단선(60초). 세 고장을 고치고(퓨즈 정상, 거름망 깨끗하고 바구니가 들어 있고 덮개가 닫힘, 리벳 09 유입 0.05L/s 미만) 빌지를 60L 아래로 1분 유지하면 끝난다. 펌프가 돌고 있을 것은 조건에서 뺐다. 교범이 C3를 평소 내려 두는 회로로 적고 있어서, 다 고친 뒤 스위치를 내린 플레이어가 이유 없이 실패하는 일이 생겼다(M1 리뷰). 제한 25분. 아무것도 안 하면 실패하고, 규칙 기반 자동 플레이어가 사람 속도로 넘길 수 있는 것을 테스트가 확인한다.

### 교범

- **`data/manual/` 10쪽**: 개요와 배치, 상황판, 진단 표, 절차 4개, 침수 대응, 공기와 몸, 소음 표. 절차의 `title`이 교범에 그대로 나와야 한다(테스트).
- **표시 단위**: 시뮬레이션의 정규화 전압 × 120 = 볼트, 전류 ÷ 120 = 암페어, 배수량 L/s × 60 = L/분. 계기 눈금, 전압계(0~150V), 배전반의 퓨즈 정격 표시, 교범이 모두 같은 단위를 쓴다.
- **교범 본문에는 게임 조작 키를 쓰지 않는다.** 교범 오버레이의 첫 장은 이번 임무의 지시서(경과 시간과 정상 유지 시간 포함), 마지막 장은 '조작 안내'다.
- **마크다운 부분집합**: 제목, 문단, 목록, 표, 굵게, 구분선. `game/scripts/UI/MarkdownBb.cs`가 BBCode로 바꾼다.

### Godot

- **장면은 코드로 짓는다** (`game/scripts/World/Submarine*.cs`). 좌표는 x 0(후방 끝)~8(전방 끝), z −1.2(좌현)~1.2(우현), 바닥 0, 천장 2.2. 해치 격벽 x = 2.7, 전방 틀 x = 5.4.
- **배치**: 전방 끝벽에 상황판, 전방 바닥 아래 축전지 우물(격자 너머로 셀과 물이 보임), 중앙 우현 배전반, 중앙 좌현 사물함과 폐기함과 수동 펌프, 후방 좌현 전동 펌프와 흡입 거름망과 세척통. 빌지 칸마다 수위 유리관(센서를 거치지 않는 진짜 수위, 현장 확인 수단). 해치 문은 후방 쪽으로 열린다(중앙의 사물함과 배전반을 가리지 않게).
- **Godot은 판정하지 않는다.** 물체는 손동작과 손에 든 것으로 명령을 고를 뿐이다. 예외처럼 보이는 두 가지는 손이 느끼는 물리다: 수동 펌프 손잡이는 한 번 퍼낸 뒤 돌아오는 동안(시뮬레이션의 `HandPumpBusy`) 움직이지 않고, 망치는 한 번 휘두르는 데 0.45초 걸린다.
- **손동작**: 누르기(소켓, 사물함 칸, 폐기함, 해치, 버팀목), 위아래로 끌기(칼날 스위치, 덮개), 원 그리기(볼트, 반시계 1.5바퀴 풀기, 시계 1.5바퀴 조이기), 올렸다 누르기(수동 펌프), 좌우로 문지르기(세척통에서 솔질), 누를 때마다 치기(나무망치, 코킹), 대고 있기(전압계). SPEC 7절의 Valve(돌리기)는 M1에 대상이 없어 만들지 않았다.
- **화면에 띄우는 것**: 조준점, 조준한 물체의 이름과 손동작 이름, 든 도구와 물건, 거부되었을 때 '손이 느낀 결과' 한 줄(예: "볼트가 덮개를 누르고 있어 열리지 않는다"). 다음에 할 일은 말하지 않는다. 물체 이름표는 회색 상자 단계의 편의라서 M5에서 다시 본다.
- **작업 시점(F)**: 배전반, 흡입 거름망, 사물함, 상황판. 카메라가 붙고 마우스 포인터로 조준한다.
- **웅크리기**는 낮은 곳(거름망, 축전지 우물 격자)을 가까이 보는 데 쓴다. 바닥 아래로 기어 들어가는 공간은 M2(케이블 챔버, 후방 빌지).
- **쥔 물건이 먼저**: 버팀목을 쥐고 이음새를 누르면 무엇을 들었든 버팀목을 댄다. 맞는 명령이 없는 조합도 가장 가까운 명령을 보내서 시뮬레이션이 거부 사유로 답하게 한다.
- **시간**: 지시서를 읽는 동안에는 멈춘다. 교범과 메모장을 펴 둔 동안에는 흐른다(SPEC 6절 duration 원칙).
- **배전반 회로 표시등**: 회로마다 부하 단자 아래 작은 전구. 부하 쪽에 물린 전구라서 센서가 아니라 진짜 통전 상태를 보이고, 밝기는 버스 전압에 비례한다. SPEC 5절 ELC-01의 '해당 회로 표시등 소등'.
- **빛**: 실내등 밝기는 버스 전압에 비례하고(SPEC 4, 11절), 전압이 낮으면 깜빡인다(깜빡임만 표현 층 난수). 구역 경고등은 상황판과 별개. 실내등이 꺼져도 움직일 수 있게 아주 어두운 환경광(0.04)을 둔다. 시뮬레이션 상태와 상관없는 유일한 빛이다.
- **소리**: `AudioStreamGenerator` 합성음. 손동작 소리는 명령이 다음 틱에 받아들여졌을 때만 낸다. 펌프와 팬 회전음(부하가 빠지면 음이 오름), 흡입구 자갈 소리(막힘), 역류 소리, 풀린 볼트로 공기 새는 소리, 누수 지점마다 3D 쉿 소리, 경보 벨, 손동작 소리, 숨소리(이산화탄소). 헤드리스에서는 만들지 않는다.
- **확인 도구**: `--smoke=프레임`, `--autotest`(손동작으로 위기를 넘기고 해치, 펌프, 감전, 작업 시점까지 확인), `--screenshot=폴더`. `tools/godot-check.sh`가 빌드부터 차례로 돌린다. 헤드리스 창은 기본이 정사각형이라 자동 플레이어가 1600×900으로 맞춘다.

## 2026-10-27 · M2 (설계)

설계는 독립 설계안 세 개(데이터 중심, 플레이어 경험 중심, 위험 관리 중심)를 종합했다. 자세한 것은 `docs/plans/M2-design.md`, 요약은 `docs/plans/M2.md`. 아래 열린 질문은 사람의 상시 지시("알아서 계속")에 따라 추천 기본값으로 정했다. M2 플레이 테스트에서 바꿀 수 있다.

- **범용 장치 엔진**: 손이 닿는 것은 닫힌 종류 일곱 개(볼트류, 덮개, 소켓, 밸브, 조절 손잡이, 작업, 레버)와 만져 보기로 나누고, `data/fixtures/*.json`에 정의한다. 조건은 시나리오 assert 문법이고, 고장 여부·상황판·단서·계기·사건 경로는 조건에 쓸 수 없다(판정은 물리 상태로만). 효과는 닫힌 목록, C# 갈고리(hook)는 닫힌 등록부이고 하나 늘 때마다 여기 적는다.
- **불변 조건**: M0·M1 기준 해시는 정해진 때에만 다시 만든다. SimWorld에 새 필드를 만들지 않고 새 상태는 데이터의 상태 부품 속성에 둔다. 모듈은 상태 부품이 있을 때만 돈다. 새 규칙은 기본 상태에서 정확히 아무것도 바꾸지 않는다. 사건 종류는 끝에만 더하고 사건 수는 0이 아닌 것만 저장한다.
- **도구**: 들고 다니는 물건. 해치 격벽의 공구판과 5칸 공구띠. 1은 빈손, 2~6은 공구띠 칸이고 처음 공구띠는 M1 도구 다섯 개 그대로(M1 키와 테스트가 그대로 맞는다). 쇠망치 ID는 `engineer_hammer`(M1 테스트가 `tool.hammer`를 문법 오류로 요구한다).
- **바닥의 도구**: 감전이나 물 분출 때 든 도구를 떨어뜨리고, 10도 넘게 기울면 바닥의 도구가 3초마다 한 구역씩 낮은 쪽으로 구른다. 공구띠와 공구판의 도구는 구르지 않는다.
- **수심**: M2 훈련에서는 수심을 고정한다. 순부력은 조회값으로만 계산하고, 수심이 움직이는 것은 M3(항해)부터. 지금 바꾸면 M0·M1의 침수 결과가 바뀐다.
- **증기 축압기**: 임무 중 다시 채워지지 않는다. 정식 수리를 위해 증기를 빼면 윈치 보조 동력을 잃는다. 채우는 수단은 M7 발전기.
- **한정 재고**: 진공관 2개(소나와 사이펀 증폭기에서 빼서 쓸 수 있음), 탄소봉 2쌍, 자이로 베어링 1개, 예비 셀 1개(점퍼는 언제나 쓸 수 있음). 나머지는 넉넉하고, 임무 검증기가 한정 재고의 수요가 재고와 빼서 쓸 수 있는 수를 넘지 않는지 본다.
- **위험 세기**: 화상 −0.12, 1.2초(증기는 데임으로 보임). 물 분출 −0.10, 2초, 30L가 쏟아진다. 감전과 끼임은 M1 그대로. 윈치 헛돎은 새 위험이 아니라 끼임이다.
- **응급 수리 수명 (가안)**: 팬 손으로 돌리기 8분, 베어링 기름칠 가동 10분, 망치로 푼 밸브 10분 또는 조작 3번, 이음 감기 최대 압력에서 약 15분, 접점 조이기 부하에서 약 20분, 브러시 스프링 조정은 마모 4배.
- **진단 보조**: 배전반 회로별 전류계, 상황판 램프 시험 단추, 선내 시계, 분기함 절연을 재는 브리지 단자를 둔다. 1930년대에 있었을 법하고, 화면 UI 없이 진단을 공정하게 한다.
- **느낌과 냄새 줄**: "뜨겁다", "타는 냄새" 같은 한 줄은 M1의 '손이 느낀 결과'처럼 회색 상자 단계에서 허용하고 M5에서 다시 본다.
- **숨은 결함**: 화면에 알리지 않는다. 늦게 나타나는 증상으로만 보이고, 교범의 '순서를 어기면' 항목이 결과를 솔직하게 적는다.
- **틀린 교범 (SPEC 7절)**: M2에 예 하나. 축 패킹 누름판 단계에 앞 기관사의 연필 정정이 적혀 있고, 시뮬레이션은 연필 쪽이 맞다.
- **분기함 위치**: 구역별(C3·C8 후방, C4·C5 전방, 나머지는 배전반 아래). 습도는 선내 하나에 구역별 바닥 물 튐을 더한다.
- **사이펀 기록기 위치**: 전방 통신 책상. DESIGN은 중앙에 두지만 중앙 좌현 선반은 수동 펌프 손잡이와 부딪힌다.
- **소리**: 합친 사운드 키트를 M2에서 연결하고 시뮬레이션 단서로 움직인다. M2 플레이 테스트에서 소리로 고장을 가를 수 있는지 보고, 음색은 M5에서 판단한다.
- **훈련 고르기**: 지시서 화면에 `m2-*` 훈련과 m1-crisis를 고르는 목록. M3의 임무 흐름이 대신한다. `--mission=`은 그대로.
- **무작위 고장**: 새 고장 17종은 M2에서 발생률 0. 마모로 생기는 고장만 저절로 생긴다. 발생률은 M3에서 임무와 함께 맞춘다.
- **교범 제목 규칙**: 절차 제목은 장 제목이나 `##` 절 제목이어도 된다. 한 고장의 응급과 정식 수리가 한 장에 들어간다. 시뮬레이션 테스트와 Godot 오버레이 검사를 함께 바꾼다.
- **공기와 축전지 속도 (SPEC 15절, M2까지)**: SPEC 수치를 그대로 두고 M2 플레이 테스트에서 묻는다.
- **2차 고장 잘라 내기**: 완료 기준 점검(WP16)에서 일정이 밀리면, 2차 고장의 Godot 장비와 계산 도구 다듬기를 M3로 넘긴다. 시뮬레이션, 수리, 테스트, 교범은 M2에 다 넣는다.
- **새 장비의 모습**: 회색 상자 대신 합친 아트 키트(`game/scripts/Art/`)로 짓는다. 기존 M1 장비의 모습을 바꾸는 것은 M5.

## 2026-10-27 · M2 (WP0 기준 해시 정책)

- **기준 해시는 세 묶음이다.** `golden-data`(얼린 데이터), `golden-scenarios`(M0 시나리오 16개의 얼린 사본), `golden-hand`(M1 손 수리 기록 6개, 1초마다 해시)와 위기 한 판(`mission-m1-crisis`), 리플레이 두 개. 새 시나리오는 `sim.tests/scenarios/`에 더해도 기준 해시에 들어가지 않는다.

- **확인 도구**: `tools/check-all.sh`(dotnet test와 Godot 확인; Godot이 없으면 크게 실패), `tools/fetch-godot.sh`(체크섬 확인), `tools/godot-check.sh 묶음...`(crisis, hands, workviews; 작업 묶음마다 늘린다).

- **추진 조회 경로**: `propulsion.throttle`, `propulsion.sparking`, `propulsion.thrust`(스로틀 × (1 − 0.5S)), `propulsion.rpm`(추력 × 300 × 버스 전압, 불꽃이 튀면 흔들림).
- **축 회전계 바늘**: 항법(WP14)의 계기 `tachometer`가 쓰는 `nav.rpm`은 `tuning.power`가 있으면 `BrushGear.Rpm` × (항법 maxRpm / 동력 nominalRpm)을 따른다. 그래서 PWR-02 때 흔들리고 NAV-02 때는 고르다(진단 쌍 '거리가 틀림'). PWR-02와 C8 퓨즈의 구별은 C8 전류계로 본다.
- **열린 우물 위를 사람만 밟는 층** `Submarine.PlayerOnlyLayer`(8): 플레이어 충돌 마스크에만 있고 조준선 마스크에는 없다.
- **버리는 소리**: 손으로 누른 폐기 자리에서 나고, 손에 든 물건이 무거우면(items.json heavy) 무겁게 낸다.
- **덮개 안 장치를 겨냥하는 방식이 둘이다**: WP8은 `AutoPlayer.Approach`가 자리 표(StandPoints)를 쓰게 했고, WP11은 fixtures 묶음에서 `AimFromStandPoints`를 쓴다. 둘 다 같은 자리 표를 쓰므로 그대로 두고, WP16의 Godot `drill:<mission>` 묶음을 만들 때 하나로 모은다.
- 합칠 때 본선이 고친 것: 스프링 응급 뒤 불꽃이 돌아오는 시간을 실제(약 4.97분)에 맞춰 교범·시험·보고서 모두 4~10분, 물건 이름 '완전히 죽은 셀', 20쪽 만지기 낱말, 03쪽 전압계 눈금에 셀의 30V 눈금.
